# Cost of Ward on the Java corpus of JavaCorpusSmokeTest (#564). Hand-written from one measured run; no test compares it.
# Measured 2026-11-15 with the jar of this change (java -jar ward.jar, OpenJDK 25.0.4, default heap), on an Apple M4 with
# 10 cores and 32 GB, through /usr/bin/time -l. Other builds ran on the machine at the same time, so the wall times are
# upper bounds; the user CPU time is beside each.
# Rule set: preset standard, languages java, plus every Java security rule (1,058 rules), default options.
# Each project had only a ward.toml with the ward check and that ward-rules.toml; nothing of the project was built.
#
# run | files | lines | findings | wall time | user CPU | peak memory
commons-lang    | ward check, cold   | 638 | 213,292 | 29,563 | 446.9 s | 556.2 s | 3.59 GB
commons-lang    | ward check, cached | 638 | 213,292 | 29,563 |  46.2 s |  31.9 s | 1.98 GB
commons-lang    | ward format --check | 638 | 213,292 | 595 files need formatting, 0 refused | 28.7 s | 20.6 s | 0.68 GB
spring-petclinic | ward check, cold   |  50 |   4,297 |    491 |  31.7 s |  34.5 s | 0.45 GB
spring-petclinic | ward check, cached |  50 |   4,297 |    491 |  20.1 s |  12.7 s | 0.35 GB
spring-petclinic | ward format --check |  50 |   4,297 | 45 files need formatting, 0 refused | 4.9 s | 4.9 s | 0.44 GB
#
# The cold and the cached run report the same findings. The CLI counts more findings than the report of the test
# (28,153 places in both projects), because the gate also runs the project-wide checks (duplication, for one) and counts
# every finding, where the test counts a rule once per line.
#
# Cost per file, cold, beside this repository's own run (#491: 263 s and 9.0 GB for 3,920 files with 318 rules):
#   commons-lang     0.70 s per file, 2.1 ms per line, 0.66 ms per file and rule
#   spring-petclinic 0.63 s per file, 7.4 ms per line (mostly start-up: 86 lines per file)
#   this repository  0.067 s per file, 0.21 ms per file and rule
# So the cost per file is about ten times this repository's, and about three times per file and rule. The files of
# Commons Lang are long (334 lines on average, 3 above 5,000 lines), and the run has 3.3 times the rules. The memory
# does not follow the same line: 3.6 GB for 213,000 lines against 9.0 GB.
# The cached run still takes 46 s for 638 unchanged files, which is the number to look at for the edit loop.
# The rule engine alone, as the test runs it (no project-wide checks, no cache, one JVM), took 150 to 240 s for both
# projects.
#
# Before this change the run did not finish cleanly: one valid file (a fuzz regression test with a string literal of
# several thousand characters) ended 25 data-flow and taint rules with a StackOverflowError, and ward format refused one
# PetClinic file as "formatting is not stable".
