# AGENTS.md

## Architecture

- Organize production packages layer-first as `domain/<feature>`, `application/<feature>`, and `infrastructure/<feature>`.
- CLI commands are inbound adapters under `infrastructure/cli/<feature>`; shared Picocli plumbing lives in `infrastructure/cli`.
- Dependency direction is `infrastructure.cli → application → domain`; outbound adapters under `infrastructure/<feature>` implement domain ports. CLI adapters must not depend on concrete outbound adapters or perform filesystem/process work.
- Keep domain models free of I/O and framework implementations; application orchestrates domain contracts without depending on infrastructure. `ArchitectureBoundaryTest` enforces bytecode boundaries, `ArchitecturePlacementTest` placement, `ArchitectureFeatureGraphTest` feature dependencies, and `ArchitectureToolchainTest` the toolchain slices of every feature; `ArchitectureRuleFixturesTest` proves the rules reject violating fixtures.
- Toolchain-specific classes live in `<layer>/<feature>/<toolchain>/` for every feature, where `<toolchain>` is `jvm`, `gradle`, `maven`, `node` (with `node/turbo`), `python` or `swift`. Toolchain slices do not depend on each other, across features and layers, except that `gradle` and `maven` may use `jvm`. Domain toolchain packages are shared vocabulary that any layer may import. A feature root in `application` or `infrastructure` names a toolchain class only if `ArchitectureToolchainTest` allowlists it, with its reason.
- Raw-key terminal input uses the `RawTerminal` port and POSIX adapter; do not launch `stty` or another process from CLI code. Route filesystem checks through application use cases and domain ports.
- `QualityGate` is the extension point; update `QualityGateFactory` and `ward.toml` together when adding a gate.
- `dev.ward.config.WardComponent` wires Dagger at compile time; preserve the explicit constructor graph for native-image compatibility.
- Native images contain only classes seen at build time. Do not call APIs that build classes at runtime: `MethodHandleProxies`, `MethodHandles.Lookup#defineHiddenClass` / `defineClass`, and similar (`java.lang.classfile`, custom class loaders). `NativeImageCompatibilityTest` rejects them. Register any `java.lang.reflect.Proxy` interface, reflective type, or FFM downcall in `ward-cli/src/main/resources/META-INF/native-image/dev.ward/ward-cli/reachability-metadata.json`.

## Adding a toolchain, language or tool

Ward resolves behavior along three axes. Add classes and rows; do not add `BuildTool` or `Language` branches outside the owning support. `GateCatalogContractTest`, `PomToolsContractTest` and `FindingSourceContractTest` name any missing piece.

- **Toolchain** (`domain/project/Toolchain`, from `BuildTool`): put its init code in `application/init/<toolchain>/` (`jvm`, `node` with `node/turbo`, `python`, `swift`, `openapi`) and its outbound adapters in `infrastructure/init/<toolchain>/` (`gradle`, `maven`, `node` with `node/turbo`, `python`, `swift`). Implement `ToolchainInitSupport` (gates, preset gates, CI setup, omissions, notes, reuse of existing tests) and register it in `InitToolchains`. Override `OwnedFileSupport` for agent rules, partial-run tables (`partialTable`, `partialGates`) and `.gitignore` entries (`gitignoreEntries`), and `MemberSupport` for Turborepo-style members. Implement `RuleFileTargets` and bind it in `InitBindingsModule`. Implement `BuildToolConfiguration` and register it in `BuildToolBindingsModule`; implement `ToolchainFinding` for its doctor checks and add its case to `BuildToolFindings.forToolchain` (see Design patterns). New toolchain code goes in the `<toolchain>` subpackage of each layer and feature it touches (for example `infrastructure/finding/swift/`), not in the feature root. Toolchain subpackages must not depend on each other, and feature roots may name a toolchain only in the classes allowlisted in `ArchitectureToolchainTest`.
- **Language**: add the `Language` constant and its detection in `infrastructure/project` (from sources, not build files); implement `SourceLanguageGates` for its toolchain (analysis gates and preset gate sets) and add it to that toolchain's language map. A language without an entry fails init by design.
- **Tool**: add its row to `QualityGateDefinitions` (ID, display name, phase, learning); offer it from a `SourceLanguageGates`; add its build-file entry for each build tool (`PomTools` and `ManagedPluginCatalog`, Gradle `PLUGINS` or `GradleBuildBlocks`); add optional rows in `PartialCheckDefaults`, `AgentRulesTemplate`, preset rule files and a `GateFindingSource`. Update `ward.toml` and the `website/` gate docs.

## Design patterns

Pick the pattern from the scenario, and copy the existing example rather than inventing a new shape. Use a pattern only when the scenario is there; a single case with no variation needs no pattern.

| Scenario | Pattern | Example in this repo |
|---|---|---|
| Behavior varies by a closed enum (`Toolchain`, `BuildTool`) | Strategy behind a factory | `ToolchainFinding` → `BuildToolFindings.forToolchain` |
| Many interchangeable checks chosen by id or config | Strategy + factory | `QualityGate` → `QualityGateFactory` |
| Variants map to Dagger-provided support objects | Registry (`Map`) | `InitToolchains` |
| Domain needs I/O or a platform call | Port (domain interface) + adapter (`infrastructure`) | `RawTerminal` → `PosixRawTerminal`; `ProjectInspection` → `FileSystemProjectInspection` |
| A use case coordinates several domain ports | Facade (application service) | `CheckService`, `DoctorService` |
| Callers should observe progress without knowing the sink | Observer (listener interface) | `CheckProgressListener` |
| Immutable data passed between layers | Value object (record) | `Project`, `Finding` |
| Wiring the object graph | Constructor injection through Dagger | `WardComponent`, `ProjectBindingsModule` |

Rules for each pattern:

- **Strategy.** Declare the interface in the layer that owns the behavior (`domain` for ports, `application` for doctor and init checks). Keep single-method interfaces `@FunctionalInterface` (PMD `ImplicitFunctionalInterface`) and package-private unless another package needs them. Name the method for what the caller does, with a verb (`check`).
- **Implementations.** Name them `<Variant><Feature>`. Make them `final` and stateless. Keep each private helper in the one implementation that uses it; extract a package-private helper only when two implementations need the same code.
- **Factory.** A `final` class with a private constructor and a static `forX(...)` method. Use an exhaustive `switch` expression. Checkstyle requires a `default`, so map unsupported variants to a warning implementation, not an exception. Stateless implementations may be created per call.
- **Registry.** Use a `Map` when the values are injected objects. Use a `switch` when each variant has its own logic. Use a table of rows (such as `QualityGateDefinitions`) when the variants are only data.
- **Port and adapter.** Put the interface in `domain` with no I/O types leaking into it. The adapter lives in `infrastructure/<feature>` and is wired in a Dagger module. CLI code uses the port and never the adapter, and it does not start processes (see Architecture).
- **Facade.** Keep it thin: it orchestrates ports and domain objects, and holds no parsing or I/O logic itself.
- **Observer.** Keep listeners optional with a no-op default, and do not let a listener change the result of the operation.
- **Value objects.** Use records for data crossing layers. Copy collections in and out, as SpotBugs requires.

Avoid in this codebase:

- Reflection, `java.lang.reflect.Proxy`, or runtime class generation for decorators or proxies. Native images only contain classes seen at build time (see Architecture), so use explicit wrapper classes instead.
- Static mutable state, and the Singleton pattern. Use a Dagger-scoped object injected through the constructor.
- Field injection, as stated under Code Style.
- Generic "manager" or "helper" classes that gather unrelated variants. Name the class after the one variant or feature it serves.
- A pattern added for one case. Wait for the second variant, then extract it.

Tests:

- Test each strategy through the caller's public behavior (for example `DoctorNodeTest`).
- When a factory or registry covers an enum, add a test that every constant maps to an implementation, so a new constant without one fails the build.
- New behavior behind a port is tested with a fake implementation, not the real adapter (`FakeCommandExecutor` for processes).

## Code Style

- Use constructor injection; do not add field injection.
- Keep each method's branching small: when a method gains a `switch` or several `if`s, move each case into its own private method, so the body only dispatches and cyclomatic complexity stays under 10.
- Spotless with Google Java Format is the Java formatter; run `./mvnw spotless:apply` to format and `./mvnw spotless:check` to verify. Spring/JPA and code-generation workflows are not configured.
- Fix the underlying cause of compiler and static-analysis findings. Do not add `@SuppressWarnings`, `@SuppressFBWarnings`, `NOPMD`, exclusions, disable checks, or lower thresholds to make verification pass. Preserve behavior and test coverage when refactoring. If a finding appears to be a framework limitation or false positive, explain it with evidence and request explicit review before introducing a suppression or workaround.
- Commands from `ward.toml` run from the project root as argument vectors, never through a shell.
- When implementing or changing operational behavior, add useful JUL diagnostics at meaningful decision and execution boundaries when logs would aid troubleshooting. Keep logs invocation-scoped, stderr-only, and safe: never log secrets, prompts, configuration or environment contents, raw argument vectors, or captured process output.

## Rule catalog

- `ward-cli/src/test/resources/catalog/*.toml` holds one `[[rule]]` row per Ward rule concept, split by Checkstyle category or tool and listed in `catalog/files.txt`. A row gives `ids` for ids that differ from `ward:<language>/<name>`, and its counterpart rule ids per tool, plus the reason of each `not-applicable` language in `not-applicable`. The status per language is not in the row: it lives in `catalog/status/<language>/<catalog file>.toml`, one sorted line per row (`row-name = "implemented"`, `"not-applicable"`, or `{ status = "planned", issue = "#N" }`), so a Java PR and a Swift PR that flip the same row touch different files. Implemented rows take category and presets from the rule definition. A rule of a replaced tool is in exactly one row, or in `ward-cli/src/test/resources/catalog/upstream/<tool>-out-of-scope.toml` with a reason.
- `ward-cli/src/test/resources/catalog/upstream/<tool>-<version>.txt` pins each tool's rule ids; the header names the command that generated it. After a tool upgrade regenerate the list; `UpstreamCoverageTest` then names every new rule to classify.
- Implementing a planned rule: add the rule definition, set the row's line in that language's status file to `"implemented"`, and add `ward-cli/src/test/resources/rules/<language>/<rule-name>/{violating.<ext>,expected.txt,passing.<ext>}`. `expected.txt` has one `line:column` per finding. `RuleCatalogFixturesTest` runs every implemented pair; a rule that needs types adds a `types.json` (see `FixtureTypeFacts`).
- The rule reference under `website/src/content/docs/reference/rules/` and `reference/rules.mdx` is generated and gitignored; never commit it. The website workflow (`.github/workflows/docs.yml`) writes it before Astro builds. To preview it locally run `./mvnw -Dtest=RuleReferenceTest -Dward.rules.reference.write=true test`; `RuleReferenceTest` only smoke-tests the generation.
- Rule files are listed per language, so parallel rule PRs do not collide: add a rule file to the sorted list of its module (`JvmRuleFiles` for Java and Kotlin, `NodeRuleFiles`, `PythonRuleFiles`, `SwiftRuleFiles` under `ward-lang-*/src/main/java/dev/ward/analysis/application/<lang>/`), and the TOML under that module's `src/main/resources/rules/`. `ClasspathRuleSource` joins the lists through the Dagger set in `RuleBindingsModule` and sorts them.
- A declarative check (`check = "<name>"` in a rule body) is registered by name in a `CheckProvider`: `JvmCheckProvider` and `PythonCheckProvider` in their `ward-lang-*` modules, `CoreCheckProvider` (ward-cli) for checks that several languages share. Put the new check class (package `dev.ward.analysis.domain.rule.check`, shared with the engine's generic checks) and its factory entry in the module of its language and add its factory to one of that module's check families; `JvmFixturesTest` and `PythonFixturesTest` run the fixtures under `ward-cli/src/test/resources/rules/` of every rule whose check the module provides, so the module's own JaCoCo bundle counts them (the catalog contract tests stay in ward-cli); `DeclarativeChecks` looks names up in `CheckRegistry`, which fails when two providers register the same name. A new language module with checks adds its provider to `BundledLanguages`.

## Quality Gate Rules

Gates in `ward.toml`; edit hooks run the `default` profile (format, checkstyle, pmd, gitleaks) on edited files. Checkstyle and PMD also cover tests.

- Checkstyle (`config/checkstyle.xml`): file ≤500 lines, method ≤60, ≤5 params, cyclomatic ≤10; Javadoc on public types and methods; no magic numbers (use named constants); no star/unused imports; no `catch (Exception|RuntimeException|Throwable)`; no empty catch; `switch` needs `default`; one declaration/statement per line; no field-hiding locals/params except constructors and setters.
- PMD (`config/pmd-ruleset.xml`): all errorprone, bestpractices, design, codestyle, multithreading, performance, security categories minus listed excludes. Mark locals and parameters `final`; no `var`; compare against named constants, not literals, in `if` conditions; do not call `new` inside a loop body (map with a stream or extract a factory method); ≤8 duplicate literals per file; keep classes small (design rules flag god classes, too many methods/imports, coupling, cognitive complexity).
- SpotBugs: effort Max, threshold Medium; only generated Dagger/Fory classes excluded. Copy mutable collections in and out of records/constructors.
- Coverage (JaCoCo): bundle ≥85% line, ≥75% branch. Mutation (PIT, `ci`): ≥60%; pull request CI mutates only the domain/application classes the change touches (`PIT_TARGET_CLASSES`), releases mutate all. New code needs tests that assert behavior.
- ArchUnit gate runs a fixed test list; add any new architecture/native contract test to that command.
- Enforcer (`config/enforcer-rules.xml`): pin every plugin version, no dynamic versions, converging dependencies, Maven ≥3.9.
- License: no GPL/AGPL dependencies.
- gitleaks: no secrets, including in tests and fixtures. Semgrep `p/java` and Trivy (any vulnerable dependency, including `website/`) run in `ci`.

## Testing

- JDK 25 and Maven wrapper are required: `./mvnw -q test`.
- Run one test with `./mvnw -Dtest=ClassName#methodName test`.
- CLI integration tests use the offline fixture `ward-cli/src/test/resources/fixtures/maven-project` and its stub `mvnw`.
- Use `FakeCommandExecutor` for process tests. Existing test names use descriptive camelCase.
- `NativeInitTerminalSmokeTest` drives a built executable's `init` wizard through a pseudo-terminal and is skipped unless `-Dward.native.binary` is set: `./mvnw -Dtest=NativeInitTerminalSmokeTest -Dward.native.binary=target/ward test` after `native:compile`.
- `NativeWardGateSmokeTest` runs a built executable's `ward` gate twice over a project with one seeded violation per engine language (Java, TypeScript, JavaScript, Python, Swift, Kotlin), plus a layer, a cycle and a taint finding, and checks that the cached second run prints the same JSON. It is skipped unless `-Dward.native.binary` is set; CI runs it with `NativeInitTerminalSmokeTest` on Linux and macOS.
- `NativeFormatSmokeTest` runs a built executable's `ward format` over one unformatted file per engine language: `--check` exits 1, a write formats the files, and a second `--check` exits 0. It is skipped unless `-Dward.native.binary` is set and runs in the same CI step as `NativeWardGateSmokeTest`.
- `GradleMutationJava25SmokeTest` runs the generated Gradle `pitest` task on Java 25 and is skipped unless `-Dward.gradle.binary` points to a Gradle executable (needs network).
- `KotlinResolutionReferenceTest` compiles the `kotlin-resolution` fixture with a real `kotlinc` and `javac`, imports the classes with ArchUnit, and asserts the file edges equal the committed `archunit-edges.json`. It is skipped unless `-Dward.kotlinc.binary` names the `kotlinc` of a Kotlin distribution whose `lib/kotlin-stdlib.jar` sits beside `bin/`: `./mvnw -Dtest=KotlinResolutionReferenceTest -Dward.kotlinc.binary=<kotlinc> test`. `KotlinResolutionGraphTest` checks the ward graph against the same golden list offline, except the one dependency that only type inference shows. The `Ward ci profile` job runs it with the pinned Kotlin release.
- `JavaTypeSidecarSmokeTest` starts the real Java type sidecar (`WardJavaTypes.java`, run by `java` in source-launch mode) on the `type-sidecar/java` fixture and checks that a call's type is `java.lang.String`, a primitive is `int`, and an unresolvable library type is absent. It is skipped unless `-Dward.sidecar.java=true`, and needs a `java` on `PATH` with `jdk.compiler`: `./mvnw -Dtest=JavaTypeSidecarSmokeTest -Dward.sidecar.java=true test`. `TypeScriptTypeSidecarSmokeTest` starts the real TypeScript sidecar (`ward-ts-types.mjs`, run by `node`) on the `type-sidecar/typescript` fixture and checks that `config.port` is `number` and an unresolved name is absent. It is skipped unless `-Dward.sidecar.typescript=<dir>` names a directory whose `node_modules` installs `typescript` (for example after `npm install typescript@5.9.3` in a scratch directory): `./mvnw -Dtest=TypeScriptTypeSidecarSmokeTest -Dward.sidecar.typescript=<dir> test`. `ProcessTypeSidecarTest` and `SidecarResourcesTest` run offline.
- `SwiftCompatibilityMatrixTest` runs each row of `ward-cli/src/test/resources/swift-matrix/cells.csv` (`xcode,buildtool,preset,fixture`) through the real CLI with that Xcode selected for the Ward process through `DEVELOPER_DIR`: `ward init --preset <preset> --yes`, a clean `ward check --profile ci`, then the seeded violations in `ward-cli/src/test/resources/swift-matrix/violations/<fixture>/`, which must fail every selected gate except `swift-coverage`. It is skipped unless `-Dward.swift.matrix=<xcode>` and `-Dward.swift.matrix.jar` are set; `-Dward.swift.matrix.developer-dir` overrides the Xcode path and `-Dward.swift.matrix.fixture=<fixture>` limits the run. - `NodeCompatibilityMatrixTest` runs each row of `ward-cli/src/test/resources/node-matrix/cells.csv` through the real CLI: `ward init --preset <preset> --yes`, a clean `ward check --profile ci` in which every gate passes, then the seeded violations in `ward-cli/src/test/resources/node-matrix/violations/<fixture>/`, which must fail every selected gate except `stryker`. The optional `packages` column lists `name@version` entries (space-separated) that the matrix writes exactly into the copied fixture's `package.json` before init, replacing the entry in the section that declares it or adding it to `devDependencies`. It is skipped unless `-Dward.node.matrix=<node value>` names the Node value of the cells to run and `-Dward.node.matrix.jar` points to the Ward jar; a cell runs only when that value equals its row's Node value, and fails when the runtime's `node --version` does not start with it: `./mvnw -Dtest=NodeCompatibilityMatrixTest -Dward.node.matrix=22.12 -Dward.node.matrix.jar=target/ward.jar test` after `./mvnw -DskipTests package`, with Node 22.12 first on `PATH`. `-Dward.node.matrix.fixture=<fixture>` optionally limits the run to one fixture's rows; CI runs one `node-matrix` job per distinct (Node value, fixture) pair in the CSV, on pull requests into `main` and on main and release builds (`verify.yml` input `compatibility-matrices`; other pull requests skip it). - Testcontainers is not configured; do not invent or claim that check.

## Security

- Treat `ward.toml` as executable trusted code; do not run it on untrusted repositories without isolation.
- Never log secrets or full request/response bodies; use environment variables for credentials.
- Integration files are ownership-marked: preserve conflict handling, rollback, and user-owned files.

## Verification (non-negotiable)

- Do not modify anything under `/config`.
- Run `ward check --profile pre-push` before finishing. Gates and profiles are defined in `ward.toml`; `ward check --profile ci` runs every gate.
- Claude Code and OpenCode edit/write hooks must invoke `ward check` through the Ward integration: `.claude/hooks/ward-edit-write` (registered in `.claude/settings.json`) and `.opencode/plugins/ward-edit-write.js`.
- `check --format json` must write only JSON to stdout; diagnostics go to stderr.
- CLI changes must update the matching documentation pages under `website/`.
- Changes to `ward init` options or behavior must update the agent skills under `skills/` in the same pull request; `AgentSkillsConsistencyTest` checks options and versions, not wording.
- `./mvnw package` builds `ward-cli/target/ward.jar`; native builds require GraalVM 25.5 and `./mvnw -Pnative -DskipTests native:compile`.
