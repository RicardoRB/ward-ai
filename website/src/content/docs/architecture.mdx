description: Ward's layered Java architecture and extension points.

Ward follows a dependency direction of infrastructure adapters → application use cases → domain
contracts and models:

```text
dev.ward
├── domain/<feature>/          Models, policies, outbound port contracts
├── application/<feature>/     Use cases and orchestration
├── infrastructure/<feature>/  Outbound adapters
├── infrastructure/cli/       Picocli inbound adapters and terminal I/O
├── config/WardComponent    Explicit Dagger composition root
└── WardApplication         Executable entry point
```

CLI adapters must not perform filesystem/process work or depend on concrete outbound adapters.
Domain models contain no I/O or framework implementations; outbound adapters implement domain
ports. Raw-key terminal input is isolated behind the `RawTerminal` port and a POSIX adapter;
`ArchitectureBoundaryTest` enforces these rules.

`QualityGate` is the gate extension point. Gate orchestration belongs in `application.gate`, supported
IDs in the domain vocabulary, and the registry in `QualityGateFactory`; configuration examples and
the [gate reference](/configuration/gates/) must stay in sync. Explicit constructor wiring also
supports native-image builds. Picocli command reflection metadata is generated from command annotations
by `picocli-codegen` at compile time, so adding a command or option does not require a manual metadata
entry. Hand-written native metadata is reserved for non-Picocli requirements such as FFM downcalls.

## Dependency inventory

Ward reads the packages a project resolves through one inventory, `DependencyInventoryService`,
instead of each check resolving the project on its own. Node, Python and Swift projects are read
from their lockfiles (`package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lock`, `uv.lock`,
`poetry.lock`, pinned `requirements*.txt`, `Package.resolved`) without running a package manager.
Maven and Gradle projects are resolved by the build tool, except a Gradle build that locks every
configuration, which is read from its lockfiles. The graph a build tool resolves is stored under
`.ward/cache/dependencies/`, keyed by the content of the build files, and reused for 24 hours. A
project that cannot be resolved is an execution error that names the file and the command that fixes
it, never an empty inventory. The inventory has no command and no output of its own; it logs only to
standard error.
