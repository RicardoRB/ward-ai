---
title: format
description: Format the project's source files in Ward style, with no external formatter.
---

`ward format` rewrites the source files of the project's engine languages (Java, Kotlin, TypeScript,
JavaScript, Python, Swift and Rust) in Ward style. It needs only the `ward` binary.

C# files (`.cs`) are formatted the way `dotnet format whitespace` formats them at its defaults; see
[C# style](#c-style).

```sh
ward format [--check] [--format text|json] [-C <dir>] [<path>...]
```

With no path, it formats every selected file in the project. With paths, it formats only those
files, or every file below a folder. Relative paths resolve against the working directory (or `-C`).

Run from a subdirectory, `ward` finds the project root: the nearest folder above with `ward.toml`,
else the nearest with `.git`. It reads that root's `.editorconfig` and formats the whole project,
exactly as a run from the root does.

## Options

| Option | What it does |
|---|---|
| `--check` | Write nothing. Exit `1` when a file needs formatting, and name each one. |
| `--format text\|json` | Output format (default `text`). With `json`, stdout holds only the JSON report. |
| `-C`, `--directory <dir>` | Run as if started in `<dir>` instead of the current directory. |

## Exit codes

| Code | Meaning |
|---|---|
| `0` | Nothing needed formatting, or every file was written. |
| `1` | With `--check`: at least one file needs formatting. |
| `2` | A file was refused or could not be read or written, a path matched no formattable file, or the `.editorconfig` configuration is invalid. |

A refused file is never written. Ward refuses a file when its formatted output would not parse, would
change a token or the syntax tree, or would not format to itself again. A file with a syntax error
is refused too, so it stays as it is.

## Output

Text output names each changed file, and each refused or failed file on stderr with its first
differing line:

```text
needs formatting src/main/java/shop/Order.java
refused tools/report.py:1: input has a syntax error
```

JSON output lists one entry per file:

```json
{
  "files": [
    { "path": "src/main/java/shop/Order.java", "status": "needs-formatting", "line": 3, "reason": "file is not formatted" }
  ],
  "error": null
}
```

`status` is `unchanged`, `needs-formatting`, `written`, `refused` or `failed`. When the run stops on
a configuration error, `files` is empty and `error` names the `.editorconfig` file, section and key.

## Settings

Ward reads the formatting options from the project's `.editorconfig` files, the same files your
editor reads. See [EditorConfig](/configuration/editorconfig/) for the keys. A project without an
`.editorconfig` gets Ward's defaults: a line width of 100, four-space indents for Java, Kotlin,
Python, Swift and Rust, and two-space indents for TypeScript and JavaScript.

## Java style

The Java formatter changes only line breaks, indentation and spaces. Every token and comment stays as
written, so imports keep their order and comments are not rewrapped.

- An argument list, a parameter list, record components, annotation arguments and array values stay
  on one line when they fit. Otherwise each item gets its own line, and the closing bracket gets its
  own line too.
- A line break inside a statement stays as a continuation line, including inside parentheses. Ward
  does not join a long expression onto one line.
- Whatever comes after a continuation line is indented from that line: a nested argument list, an
  anonymous class body, a lambda block or a switch expression.
- A line that starts with a call-chain dot, a binary operator or a conditional `?` or `:` goes one
  continuation deeper than the line it continues. In order from loosest to tightest, those are
  `?`/`:`, then binary operators, then dots. A looser line goes back to the depth of its own kind.
  A comment inside a continued statement keeps the statement's indentation.

## C# style

The C# formatter changes only whitespace, as `dotnet format whitespace` does, and never wraps a long
line. Every token and comment stays as written.

- Lines are indented by brace depth, four spaces by default (`indent_style` and `indent_size` of the
  `.editorconfig` apply). The body of an `if`, `else`, `for`, `foreach`, `while`, `do`, `using` or
  `lock` that is not a block, and the statements of a `switch` section, go one level deeper.
- An opening brace goes on its own line when its block spans lines, for types, methods, accessors,
  statements, lambdas, object initializers and switch expressions. A block that ends on the line it
  starts on, such as `{ return 1; }`, and an array initializer such as `new[] { 1, 2 }`, stay as
  written. An `else`, `catch` or `finally` goes below the closing brace of a multi-line block.
- Spaces follow `dotnet format`: around binary operators, after commas and semicolons, after
  `if`, `for`, `while`, `switch` and the other statement keywords, and none inside parentheses,
  before a call's arguments or around `.`, `?.` and `::`.
- A line break stays where it is, as a continuation line at the depth of its statement. Blank lines
  stay. `#region` and `#endregion` follow the code around them; every other directive goes to the
  first column.
- Verbatim, raw and interpolated strings and comments are copied as written.

Ward differs from `dotnet format` in a few places, and the parity test lists each one with its
reason: it keeps the inner lines of a block comment and the line breaks after a block comment, it
indents a continuation line inside a parameter list or a constraint list at the depth of its
statement (`dotnet format` keeps the source offset), it does not align the clauses of a query with
its first `from`, and it indents a label like a statement.

Ward refuses a C# file that has a conditional-compilation branch the parser skips (an `#if` whose
symbol is not defined in the file), because the formatter cannot read the code in that branch.

## Formatting in `ward check`

The [`ward-format` gate](/configuration/gates/#format-gate) runs the same formatter in `ward check`,
and reports each unformatted file as an error. It never writes a file; run `ward format` to fix them.

## Rust style

The Rust formatter follows rustfmt's defaults for what it can reach by changing only whitespace:
four-space indents, braces on the line of their item, `a + b`, `x: T`, `&mut x`, `Vec<T>`, `|x| x`,
`foo(a, b)`, `1..10` and `a.b()?`. A method chain, a binary expression or a `where` clause that you
break across lines gets one more indent level for its continuation lines. Blank lines collapse to
one and disappear after an opening and before a closing brace. Inside a macro call the formatter
keeps your spacing, except around commas and brackets.

Every token and comment stays as written, so unlike rustfmt, Ward does not:

- add a trailing comma to a list it breaks,
- join a short list or call that you broke across lines, or break a line that is too long,
- sort `use` declarations or reorder items.

On a file that rustfmt has already formatted, `ward format --check` passes. A Rust file with a syntax
error is refused and left as it is; the parser reads Rust 2021 and the 2024 raw-borrow syntax.
