`ward hook` contains the adapters that generated agent integrations call. You normally do not run it
yourself.

```sh
ward hook claude-code [-C <dir>] [--learn-after <n>] [--event-stdin]
ward hook native --agent <agent> [-C <dir>] [--event-stdin]
```

## Options

| Option | Effect |
|---|---|
| `-C`, `--directory <dir>` | Run for the project in `<dir>`. See [Nested projects](#nested-projects). |
| `--learn-after <n>` | Learn recurring quality failures after `n` occurrences (default `3`). |
| `--agent <agent>` | (`native` only) Harness whose payload and response format to use. |
| `--event-stdin` | Read the hook event JSON from stdin. It is ignored when stdin is an interactive terminal. |
| `--verbose` | Print diagnostics to stderr. See [Verbose diagnostics](#verbose-diagnostics). |

## Claude Code adapter

`ward integrate claude-code` creates `.claude/hooks/ward-edit-write`, which runs
`ward hook claude-code --learn-after 3 --event-stdin` after Claude Code's edit tools and
when Claude stops.

Without `--event-stdin`, or when the payload is empty or not valid JSON, the adapter behaves as it always has. It
runs the `default` profile gates as a `PostToolUse` check. When they pass, it returns any learning prompts as
`PostToolUse` context. When they fail, or Ward cannot run, it writes the failures to stderr and exits `2`,
which Claude Code shows to the agent so it can fix them.

With an event payload:

- **`PostToolUse`:** a [partial check](/commands/check/) runs for the edited `tool_input.file_path`. An event
  without a path runs every gate in full.
- **`UserPromptSubmit`:** the prompt is scanned for secrets. See [Prompt hook](#prompt-hook).
- **`Stop`:** the full `default` quality check runs. Findings block the stop
  once, using `decision: "block"`. When `stop_hook_active` is true, or Ward cannot run, they are shown to the
  user as a `systemMessage`. This full check also catches files changed by shell commands, which send no edit
  event. The exit code is `0`.

See [Claude Code](/integrations/claude-code/) and [learning](/configuration/learning/).

## Native adapter

`ward hook native` accepts bounded JSON from the supported harnesses, runs quality checks, and
translates the findings into the harness's response shape.

- `--agent` is required and must be a native harness ID: `codex`, `cursor`, `copilot`, `gemini`,
  `windsurf`, `cline`, `factory-droid`, or `amp`.
- Malformed, missing, or oversized payloads (over 1 MiB) fail safely and never print payload
  contents.

See [native harness integrations](/integrations/native-harnesses/).

## Prompt hook

A prompt hook blocks a prompt that holds a secret before the agent sends it to the model. It is opt-in
twice: `ward integrate <agent> --prompt-hook` (or `ward init --prompt-hook`) registers it, and it
scans only while `ward.toml` has [`[checks.secrets.prompts]`](/configuration/secrets/#scanning-prompts)
with `enabled = true`.

It needs no new command: the prompt event reaches the same adapters, `ward hook claude-code
--event-stdin` and `ward hook native --agent <agent> --event-stdin`, and the generated wrapper is
unchanged.

| Agent | Event | How a prompt is rejected |
|---|---|---|
| `claude-code` | `UserPromptSubmit` | `{"decision":"block","reason":…}` on stdout, exit `0` |
| `codex` | `UserPromptSubmit` | `{"decision":"block","reason":…}` |
| `factory-droid` | `UserPromptSubmit` | `{"decision":"block","reason":…}` |
| `gemini` | `BeforeAgent` | `{"decision":"deny","reason":…}` |
| `cursor` | `beforeSubmitPrompt` | `{"continue":false,"user_message":…}` |

The other agents have no documented prompt event that can reject a prompt, so they are unsupported and
get no prompt hook: `copilot` (its `userPromptSubmitted` output cannot block), `amp` (`agent.start` cannot
reject), `cline` (no prompt event), `junie`, `windsurf` and `opencode` (no documented way to reject a
prompt). `ward init --prompt-hook` says so for each such integration.

The input is the message and the files the prompt attaches (Cursor `attachments`) or references
with `@path` in the message. A file keeps its path, so the check's `exclude-paths` and the rules' path
filters apply to it. The message has no path: rules with a `path` filter and path-only rules do not run
on it, and allowlist `paths` do not apply; allowlist `regexes` and `stopwords` do. A path outside the
project is never read.

The block message names the rule and the place, and never repeats the secret:

```text
Ward blocked this prompt: it contains a secret.
- ward:secrets/github-pat in the message, line 2, column 1
- ward:secrets/aws-access-token in config/app.yml, line 4, column 12
Remove the secret from the prompt, and rotate it if it was ever shared.
```

If Ward cannot scan the whole prompt (a rule over its budget, an unreadable attached file, a broken rule
file), the prompt is blocked too, with the reason and no prompt text. Nothing about the prompt is written to
`.ward`, the cache or a report; with `--verbose` the diagnostics hold only rule ids and the decision.

## Nested projects

When `-C` names a project below the repository root:

- An edit event whose paths all lie outside the project runs no gate and succeeds.
- A Claude Code `Stop` event runs the full check only when a file under the project differs from
  `HEAD` in the working tree or the index.
- Projects at the repository root behave as before.

A native hook started outside every project, as the shared repository-level hooks of
[monorepos](/commands/init/#monorepos) are:

- checks each configured project (a directory with `ward.toml`) that contains an edited file, and at
  turn end each configured project with changes;
- starts findings with `Ward checked <project>:`.

## Verbose diagnostics

The inherited `--verbose` option also applies to nested hooks, for example
`ward hook claude-code --verbose`. Diagnostics are written to stderr, leaving the hook JSON
response on stdout unchanged. They never include findings, payload contents, or command lines.

## Exit codes

| Adapter | `0` | `1` | `2` |
|---|---|---|---|
| `hook claude-code` | Gates passed; always for `Stop` and `UserPromptSubmit` events | — | Gates failed or Ward could not run (reported to the agent on stderr) |
| `hook native` | Depends on the harness's hook contract; see [native harness integrations](/integrations/native-harnesses/) | | |
