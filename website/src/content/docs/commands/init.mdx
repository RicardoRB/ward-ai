`ward init` creates `ward.toml` using an interactive wizard or explicit options. It sets up Maven,
Gradle, TypeScript, and JavaScript projects; see [Node projects](#node-projects) for what changes
in a Node project.

```sh
ward init [-C <dir>] [--project <dir>]... [--preset <standard|strict>] [--integration <none|agent>[,...]] [--quality-hooks] [--remove-quality-hooks] [--ci github] [--agent-rules] [--gate <id>[,...]] [--install-tool <gate>[,...]] [--architecture <style>] [--overwrite] [--dry-run] [--accept-compatibility-updates] [--replace-scripts] [--yes]
```

<Aside type="tip">
To set up Ward together with your coding agent instead, install the
[agent skills](/integrations/agent-skills/). The `ward-init` skill inspects the project, explains
each choice for this codebase, and runs `init` with explicit options after you approve the
`--dry-run` plan.
</Aside>

## Options

| Option | What it does |
|---|---|
| `-C`, `--directory <dir>` | Start in `<dir>` instead of the current directory. See [Choosing projects](#choosing-projects). |
| `--project <dir>` | Configure this Maven, Gradle, TypeScript, or JavaScript project, relative to `-C`. Repeat for several. |
| `--preset <standard\|strict>` | Pre-select the preset's gates and rules. See [Presets and gates](#presets-and-gates). |
| `--gate <id>[,...]` | Enable these [gates](/configuration/gates/). With `--preset`, adds to the preset's gates. |
| `--integration <none\|agent>[,...]` | Install agent integrations. `none` cannot be combined with an agent. |
| `--architecture <style>` | `layered` (default), `hexagonal`, or `clean`: the layer boundaries of `[[checks.ward.layers]]` in `ward.toml`, which init always writes. The wizard asks for it under `strict`. |
| `--scheme <name>` | Xcode scheme that a Swift project's tests run, when the project has several. With `--yes`, a project with several schemes needs this option. |
| `--install-tool <gate>[,...]` | Accepted for compatibility; init installs no gate tool, so it has no effect. |
| `--quality-hooks` | Add Ward checks to the Git pre-commit and pre-push hooks. |
| `--remove-quality-hooks` | Remove only Ward's sections from those hooks. |
| `--ci github` | Write a GitHub Actions workflow that runs the `ci` profile. |
| `--agent-rules` | Write the selected gates' limits into a Ward-owned section of `AGENTS.md`. |
| `--overwrite` | Replace an existing `ward.toml` without asking. |
| `--dry-run` | Print the change plan and exit without writing anything. |
| `--accept-compatibility-updates` | Approve validated Maven plugin version updates without asking. |
| `--replace-scripts` | Replace Turborepo member scripts that already run a different command, without asking. Without it, init lists them once and asks; a declined or unanswered question keeps them. |
| `--yes` | Use defaults for unanswered questions, skip the review, approve compatibility updates. See [How questions are answered](#how-questions-are-answered). |
| `--verbose` | Print initialization diagnostics to stderr. See [Troubleshooting](#troubleshooting-with-verbose-diagnostics). |

`agent` accepts the IDs documented for [`integrate`](/commands/integrate/), including `codex`,
`cursor`, `copilot`, `gemini`, `windsurf`, `cline`, `factory-droid`, and `amp`.

## Presets and gates

- `standard` and `strict` pre-select their offline gates. `custom` (wizard only) starts with none.
- For TypeScript and JavaScript, see [Node projects](#node-projects) for what each preset selects.
- The gates you confirm are exactly the gates configured. Unticking a pre-selected gate removes its
  `ward.toml` section, build declarations, and rule file. The preset's rules still apply to the
  other gates.
- With `--preset`, `--gate` only adds gates. It never removes preset gates.
- Init does not run gates.

Some gates need extra input:

- **Architecture.** Init always writes the layer boundaries of a style (Layered, Hexagonal, or Clean;
  `layered` by default) to `ward.toml`, checked by `ward:architecture/layers`. Under `strict` the
  wizard asks for the style, and the slice cycle check and the feature independence table are
  written too; see [Generated files](#generated-files).
- **`api-compat`** needs a baseline. A Java or Kotlin project (Maven or Gradle) is offered it when a release
  tag such as `v1.2.3` is reachable from `HEAD`; otherwise `--gate api-compat` fails and says so.
  Init writes `uses = "api-compat"` and changes no build file, for either language.
  See [API compatibility](/configuration/gates/#api-compatibility).
- **`openapi-lint`, `openapi-diff`, and `openapi-compat`** are offered only when Git tracks an
  `openapi.yml`, `openapi.yaml`, or `openapi.json` in `src/main/resources` or the project root.
  With a tracked spec, `--preset` adds `openapi-lint` and `openapi-diff`, and `strict` adds
  `openapi-compat`. Init writes that path as their `spec`; see
  [OpenAPI contract gates](/configuration/gates/#openapi-contract-gates). When the project's
  framework serves HTTP (such as Spring Boot, FastAPI or Express) but has no tracked spec, init's plan
  says so and asks you to commit one first.
- **`crap`** is opt-in for Maven, Gradle, Vitest, Jest, Bun and Python projects: no preset selects it
  and the wizard lists it unselected. It needs the coverage gate (`coverage`, the test gate, or
  `pytest`) and `--gate crap` fails with exit code 2 without it. Init writes `[checks.crap]` after
  that gate, and reads the report that the `coverage` check already makes the tool write; see
  [CRAP gate](/configuration/gates/#what-ward-init-writes-for-crap). Swift, Android and Angular
  (`ng test`) projects are not offered it.
- **`vulnerabilities`**: a native check that matches the resolved dependencies against OSV advisories.
  No preset enables it. Init offers it for every toolchain, writes it with `uses = "vulnerabilities"`
  in the `ci` profile, and asks no install question. See
  [vulnerabilities](/configuration/vulnerabilities/).

### Profiles

Init assigns each gate to cumulative [profiles](/configuration/ward-toml/):

| Gates | Profiles |
|---|---|
| Fast: `ward-format`, `secrets` | `default`, `pre-commit`, `pre-push`, `ci`, `edit` |
| Slower local gates, including `compile`, `tsc`, the test runners, and custom commands | `pre-push`, `ci` |
| Environment-dependent gates | `ci` |

`default` is the same fast tier as `pre-commit`, and `ci` contains every selected gate.

## Ward rules for Java and Kotlin

For a Java or Kotlin project, init writes no separate style or bug gate, configuration file, build plugin
or package entry. The `ward` check applies Ward's own rules instead, and init writes a
`ward-rules.toml` that selects the rules of the preset:

```toml
version = 1

[select]
preset = "standard"
languages = ["java", "swift"]
```

The file starts with an ownership marker, so a `ward-rules.toml` that you wrote is kept and
reported as user-owned. With the `strict` preset the file also sets `ignore-constructor-parameter` and
`ignore-setter` to `true` on `ward:java/hidden-field`, as the former style configuration did.
See [`ward-rules.toml`](/configuration/ward-rules/) to tune the rules.

`languages` lists the JVM source languages the project has, Java before Kotlin, then Swift: `["java", "swift"]`
for a Java project, `["kotlin", "swift"]` for a Kotlin-only one, and `["java", "kotlin", "swift"]` for a
mixed one. Kotlin gets the same gates as Java. Swift's rules apply to `.swift` files only, so the Swift
entry is harmless in a project without Swift sources. TypeScript, JavaScript and Python keep their
external linters until their own migration lands, so selecting their Ward rules would report each
finding twice.

## What init changes in your build

For `coverage`, `mutation` and `sonar`, init adds missing plugins using Ward's embedded Java
compatibility catalog. `build-policy` and `api-compat` are native and add no plugin.

Earlier versions of Ward offered an `enforcer` gate that wrote `maven-enforcer-plugin` and
`config/enforcer-rules.xml`. Init no longer writes either, and `--gate enforcer` is an unknown gate.
When it finds `config/enforcer-rules.xml` it removes the file if it carries Ward's `managed-by`
marker, and keeps and reports it otherwise. The plugin entry in `pom.xml` is yours to remove. On
Maven, the `strict` preset selects `ward:build/dependency-convergence` and
`ward:build/require-upper-bound` instead; see
[moving from the `enforcer` gate](/reference/build-policy-rules/#moving-from-the-enforcer-gate).

- Existing compatible plugin versions are kept.
- For an incompatible managed plugin, init shows the current version, the compatible version, the
  detected constraints, and the file, then asks for consent. Approve with `--yes` or
  `--accept-compatibility-updates`.
- A declined update leaves the build file unchanged, and init reports that the gate was not
  reconfigured.

### Multi-module Java builds

In a multi-module Maven build, init places the `coverage` (JaCoCo), and `mutation` (PIT)
gates in each module that has Java or Kotlin sources, so
each module's configuration and report live with its code. Other gates stay in the aggregator. The
module-placed gates are the same for Gradle and Maven.

Module declarations keep their version, so a module builds the same way whether or not the aggregator
pins it. Rule files stay in the aggregator, and module declarations point at them from the
multi-module directory.

- Each module's `pom.xml` declares the plugin in its own `build/plugins`. The aggregator pins the
  plugin version in `build/pluginManagement` and declares no module gate in its own `build/plugins`,
  so each gate runs once per module. A single-module project keeps the root declaration.
- A module with no `src/main/java` or `src/test/java` directory is left out, and init names it, with
  the reason, in its output.
- `ward init --dry-run` lists each module `pom.xml` that would change. Rollback restores every pom
  init changed.
- In a Gradle build, modules that apply the `java` or `java-library` plugin and have Java sources are
  configured the same way as the Kotlin modules below.
- `ward.toml` is unchanged: a Maven or Gradle task run from the root runs in every module that has it.

### Multi-module Kotlin Gradle builds

When a Gradle build has modules that apply the Kotlin JVM plugin in their own build script (for
example `kotlin("jvm")`, `org.jetbrains.kotlin.jvm`, or a catalog `alias` for `kotlin.jvm`), init
writes the `coverage` (JaCoCo) and `mutation` (PIT) plugins and blocks into each of those module scripts, in that script's DSL. Other gates
stay in the root script.

- The root script declares a versioned module plugin once, with its version and `apply false`.
  Module scripts declare it without a version, so the version is resolved once for the project.
- The root script receives the module blocks only when it applies the `java` or Kotlin JVM plugin
  itself, so a single-module Kotlin project is configured exactly as before.
- Convention plugins, `buildSrc`, and nested builds with their own settings file are not modules.
  When a module applies the Kotlin JVM plugin only through a convention plugin, its blocks stay in
  the root script, and init says that no module applies the Kotlin JVM plugin directly.
- `ward init --dry-run` lists every module script that would change. Rollback restores every
  script init changed, and a rerun changes no script.
- The Gradle `coverage` gate fails a module that has no tests, instead of passing it: Gradle skips
  the JaCoCo report when no test wrote coverage data, so init adds a task that runs the tests and
  fails when they leave none. The `coverage` check of `ward.toml` sums the XML reports of every
  module and checks one total against its `minimum`.
- The `mutation` minimum score sums the fresh PIT XML reports of the root and each module. The
  strict preset writes its threshold there as the gate's `minimum`; the Gradle PIT block sets none.
  The generated PIT block enables the XML output that the gate reads and reruns PIT on every
  check, so a repeat run is not reported as stale.

### Java compatibility

Ward supports Java 8 to 25. Init chooses every plugin and engine version for the JDK that runs
your build, not for the JVM that runs Ward:

- **Maven:** the `Java version` that `mvn --version` (or `./mvnw --version`) reports.
- **Gradle:** the `Launcher JVM` that `gradle --version` (or `./gradlew --version`) reports. Init
  also reads the Gradle version, because some plugins need a newer Gradle.

The release the build targets (`maven.compiler.release`, `sourceCompatibility`,
`JavaLanguageVersion.of(n)`, or `options.release`) defaults to that JDK. A release above the
runtime JDK cannot compile, so init stops and asks you to run the build on a newer JDK.

Each version was run on a real JDK in Ward's compatibility matrix:

| Tool | JDK 8 | JDK 11 | JDK 17 | JDK 21 | JDK 25 |
|---|---|---|---|---|---|
| PIT | 1.17.4 | 1.30.1 | 1.30.1 | 1.30.1 | 1.30.1 |

JaCoCo 0.8.13 uses the same
version on every JDK.

Every strict gate runs on each LTS JDK from 8 to 25. When no version of a gate's tool runs on your
JDK, init leaves that gate out and configures the others. The plan, `--dry-run`, and the init
output name it:

```text
mutation omitted: info.solidsoft.pitest needs JDK 8+; this project builds on JDK 7
```

- A gate you pass with `--gate` that cannot run on your JDK stops init before it changes any file.
- In the interactive gate list, such a gate is shown as unavailable and cannot be selected.
- The Gradle `sonar` plugin needs JDK 11, so on Gradle it is omitted on JDK 8.
- Above Java 25, init configures the project exactly as for JDK 25 and warns that Ward has not been
  tested on that JDK and does not support it.
- Below Java 8, init warns that Ward supports Java 8 to 25 and may not work with that version.
- Neither warning stops init.

### Generated files

- **`ward.toml`** includes [`partial` tables](/configuration/gates/#partial-checks) for
  `ward`, `ward-format`, and `secrets`. The check after each agent edit, and the
  pre-commit hook, skip gates the change cannot affect and narrow these tools to the edited or
  staged files. Other gates, `ward check` without `--path`, the pre-push hook, and CI still check
  the whole project. `secrets` scans those files itself, so it sees changes that are not yet
  committed.
- **`ward.toml` architecture tables.** `[[checks.ward.layers]]` holds the boundary of the style, and
  `ward:architecture/layers` checks it. Under `strict`, `[checks.ward.cycles]` lists the source roots
  whose slices must not form cycles, and `[[checks.ward.independence]]` lists the feature modules that
  must stay independent.
- **The `secrets` gate** runs inside Ward, with no command and nothing to install, and writes
  `uses = "secrets"`. It is offered with `--gate secrets` and no preset selects it. See
  [secret detection](/configuration/secrets/). The `gitleaks` gate no longer exists; a configuration
  that still runs a `gitleaks` command keeps working as a plain command check, without findings.
- **The `license` gate** is native and changes no build file: init writes `[checks.license]` with
  `uses = "license"` and no `command`, for Maven, Gradle, Node, Python and Swift projects. It adds no
  plugin, version, `licenseMerges` or `licenseReport` block, and leaves such content that is already
  in a build file alone. The policy depends on the preset:
  - `standard` and `custom` write `deny = ["GPL-*", "AGPL-*"]`; `LGPL` and the Classpath Exception
    pass.
  - `strict` writes an `allow` list of Apache-2.0, MIT, BSD-2-Clause, BSD-3-Clause, ISC, EPL-1.0,
    EPL-2.0 and CC0-1.0. A dual-licensed dependency passes when one of its licenses is allowed. LGPL,
    MPL and CDDL are not listed because they need a legal decision; add an approved identifier to
    `allow`.

  A license Ward cannot find is a finding, so install the dependencies before the gate runs; Ward
  never downloads license metadata. See [License gate](/configuration/gates/#license-gate).

### Existing files

- An existing `ward.toml` is kept unless you confirm the overwrite or pass `--overwrite`.
- Preset rule files are Ward-owned. Unmarked existing rule files are kept and reported.

### First failures under `strict`

The generated rule files load as they are, so a gate that fails right after init reports a real
finding. With `strict`, expect these on most existing projects:

- `ward`: findings of the strict Java rules, such as `ward:java/magic-number`,
  `ward:java/missing-javadoc` or `ward:java/method-length`, in existing code.
- `build-policy`: `ward:build/plugin-version-pinned` is selected by `strict` on purpose, so every
  plugin needs a pinned version. See [Build policy rules](/reference/build-policy-rules/).
  - Init pins the plugins Maven adds through its default lifecycle (clean, resources, compiler,
    surefire, jar, install, deploy, and site) in `<pluginManagement>`. It uses the versions Maven
    3.9.16 binds by default and skips plugins the POM already declares. The pins appear in
    `--dry-run`.
  - The rule can still fail on other plugins, such as `maven-war-plugin`, or when a parent POM
    supplies a version. Pin those in `<pluginManagement>` with the versions the message reports.
  - Use `standard` if you do not want this rule.
- `license`: a `ward:license/not-allowed` finding for any dependency whose licenses are not all on the
  `allow` list, for example an LGPL-only JDBC driver, and a `ward:license/unknown` finding for a
  dependency that is not installed or declares no recognizable license. Add the license to `allow`
  once your legal policy approves it, install the dependencies, or set `unknown = "warn"`.

## Node projects

Init sets up TypeScript and JavaScript projects with npm, pnpm, Yarn, or Bun. Every Node tool runs
as a local dev dependency through the package manager's runner: `npx`, `pnpm exec`, `yarn`, or
`bunx`.

- A project is TypeScript when `tsconfig.json` sits next to `package.json`, or a workspace member
  has one.
- A TypeScript project's framework comes from the packages it declares in `dependencies` or
  `devDependencies`, never from file names: `vue` or `nuxt` is Vue, `svelte` or `@sveltejs/kit` is
  Svelte, `astro` is Astro, `@angular/core` is Angular, `next` is Next.js, `@nestjs/core` is NestJS,
  `fastify` is Fastify, and `express` is Express. If several match, the first in that order (Astro,
  Svelte, Vue, Angular, Next.js, NestJS, Fastify, Express) decides.
- For Vue, Svelte and Astro, the type-check gate is the framework's checker in place of `tsc`:
  `vue-tsc` (`vue-tsc --build`), `svelte-check`, and `astro-check` (`astro check`). `tsc` is not
  offered for those projects.
- For Angular, the type-check gate is `ngc -p tsconfig.app.json --noEmit`, which checks component
  code and templates. The test gate is `ng-test`: `ng test --watch=false --coverage`, run with the
  project's own test builder. Ward writes no test config for Angular and edits no `angular.json`,
  `karma.conf.js` or `tsconfig*.json`. Angular's default `vitest` dependency does not select the
  `vitest` gate; a declared `jest` keeps `jest`.
- Angular's coverage minimums are enforced only when `angular.json` sets `coverageThresholds`, and
  init writes no `coverage` check for `ng-test`. When it sets none, the plan says so, names
  `angular.json` and `karma.conf.js` as the files to set them in, and names the `[checks.coverage]`
  check with `uses = "coverage"` and a `report` path that enforces a minimum from `ward.toml`.
- Ward supports Angular 21 and 22. Before it changes any file, init reports an `INCOMPATIBLE`
  finding and writes nothing when the project declares an unsupported Angular major, a TypeScript
  version outside the major's peer range (`>=5.9 <6.1` for 21, `>=6.0 <6.1` for 22), or runs on a
  Node version outside the major's range (`^20.19.0 || ^22.12.0 || >=24.0.0` for 21,
  `^22.22.3 || ^24.15.0 || >=26.0.0` for 22). An unsupported major reports only that finding.
- `stryker` is not offered for Angular, and the strict preset omits it, because no Stryker runner
  works with Angular's test builder. The plan says so.
- A framework project whose TypeScript configuration has no inputs fails the type-check gate and
  names the file. `vue-tsc --build` reports `TS18002` for a root `tsconfig.json` with `"files": []`
  and no references, and `TS18003` for a referenced config with `"include": []`. A root with
  references to configs that have sources passes.
- Stryker mutates only the `src` folder in Vue, Svelte and Astro projects, so component files and
  tests are not mutated. Other projects keep Stryker's default.
- Any other `package.json` is JavaScript, and counts as a project only when it holds `.js`, `.jsx`,
  `.mjs`, or `.cjs` sources of its own. Init does not count files in `node_modules`, build output
  (`dist`, `build`, `out`, `target`, `coverage`), hidden directories, directories with another build
  file (such as `pom.xml`), packages that are not workspace members, or root tool configs such as
  `vite.config.js`. A package without sources, such as a monorepo root, is skipped; see
  [Choosing projects](#choosing-projects).

### Lint and style

Ward's TypeScript and JavaScript rules do the linting. Init writes no lint config, adds no lint
packages or scripts, and offers no lint gate. It writes `ward-rules.toml` with the preset and the
project's languages: `languages = ["typescript"]`, `["javascript"]`, or both. The `ward` gate then
applies Ward's rules for those languages. Formatting stays with `ward-format`, and no external
security scanner is offered, because Ward's own security rules run in the `ward` gate.

If the project already has a `ward-rules.toml` that Ward did not write, init keeps it as it is and
warns that the preset is not applied to it. A project's own lint config, if any, is left unchanged,
and Ward does not run it.

### Gates

| Gate | Command (npm) | Profiles |
|---|---|---|
| `tsc` | `npx tsc --noEmit --pretty false` | `pre-push`, `ci` |
| `vitest` | `npx vitest run --coverage` | `pre-push`, `ci` |
| `jest` | `npx jest --coverage` | `pre-push`, `ci` |
| `bun-test` | `bun test --coverage --coverage-reporter=text --coverage-reporter=lcov` | `pre-push`, `ci` |
| `coverage` | no command: reads `coverage/lcov.info` | `pre-push`, `ci` |
| `stryker` | `npx stryker run` | `ci` |
| `ward` | `ward` analysis of `ward-rules.toml` | `default`, `pre-commit`, `pre-push`, `ci` |

- JavaScript gets the same gates except `tsc`.
- The test runner is the one the project declares: `vitest`, then `jest`. A Bun project without
  either gets `bun-test`, and any other project gets `vitest` with `@vitest/coverage-v8`. Their version follows the declared `vite`: the newest pinned release whose Vite range includes it (4.1.11 for Vite 6 to 8), and 4.0.18 without `vite`.
- `secrets` is offered as for Java.
- `crap` is opt-in. Selected with `vitest`, `jest` or `bun-test`, it reads the `coverage/lcov.info`
  that the test gate writes. It is not offered for `ng-test`.

| | `standard` | `strict` |
|---|---|---|
| Gates | `tsc` (TypeScript only), and the test runner | the same, plus `stryker` |
| Ward rules (`ward-rules.toml`) | the `standard` preset | the `strict` preset |
| Coverage (`minimum` of the `coverage` check) | at least 70% of lines | at least 85% of lines and 75% of branches (Bun: lines only, because it does not measure branches, and the plan says so) |
| Mutation score | none | at least 60%, in `ci` |

A custom selection uses the `standard` coverage minimum, and `stryker` without `strict` reports its
score without a minimum.

#### Where the minimums live

The coverage minimums live in `ward.toml`, and nowhere else. After the test gate, init writes a
`coverage` check with `uses = "coverage"`, no `command`, the `pre-push` and `ci` profiles and the
preset's `minimum` (and `minimum-branches`). The test runner writes `coverage/lcov.info`, which Ward
reads; Angular (`ng-test`) projects get no `coverage` check. The check reads the report of every
member in a Turborepo workspace and compares their sum with the minimum.

- When the project has no Vitest config, init writes a Ward-owned **`vitest.config.mjs`** with the
  `v8` provider and the `text` and `lcov` reporters, and no threshold. Jest reports lcov by default,
  so init writes no Jest config. The Bun command is `bun test --coverage --coverage-reporter=text
  --coverage-reporter=lcov`, and init writes no `bunfig.toml`.
- When the project has its own config (`vitest.config.*` or `vite.config.*` for Vitest;
  `jest.config.*` or a `"jest"` key in `package.json` for Jest), init keeps it unchanged and lists
  it as user-owned. The command then passes the reporter flags, for example `npx vitest run
  --coverage --coverage.reporter=text --coverage.reporter=lcov`, and no threshold flag. A threshold
  the project's config sets still applies to the runner; Ward reads only the `minimum` of
  `ward.toml`, and the plan says so.
- Stryker reads its minimum from `stryker.config.mjs`.
- Configs written by an earlier Ward version carry a `managed-by: ward` marker: init rewrites a
  `vitest.config.mjs` without its threshold, and removes a `jest.config.mjs` or `bunfig.toml`, which
  held nothing else, and lists each in the plan. A file without the marker is never touched.

### What init changes in `package.json`

Init adds each package its gates need, at the pinned version, unless the project already declares it:

| Package | Version | Node | TypeScript |
|---|---|---|---|
| `typescript` | 6.0.3 | `>=14.17` | any (added only when missing) |
| `vitest`, `@vitest/coverage-v8` | 4.0.18, or the release for the declared `vite` | `^20.0.0 \|\| ^22.0.0 \|\| >=24.0.0` | none |
| `vue-tsc` | 3.3.12 | `>=22.12.0` | `>=5.9.3` |
| `svelte-check` | 4.7.6 | `>=18.0.0` | `^5.0.0 \|\| ^6.0.0` |
| `@astrojs/check` | 0.9.10 | `>=22.12.0` | `^5.0.0 \|\| ^6.0.0` |
| `@stryker-mutator/core` and its runner | 10.1.1 | `>=22.0.0` | none |
| `turbo` (Turborepo root) | 2.11.9 | `>=18` | none |

A declared package keeps its version. Init writes its changes only after the compatibility checks
below pass.

### Compatibility checks

Before writing, init checks each package it would add against the project's Node version (from
`.nvmrc`, `.node-version`, or `engines.node`, else 24), and each checker against the declared
`typescript` version.

- A package outside its range is an `INCOMPATIBLE` finding naming the package and the range.
  `--dry-run` lists it, and applying fails without changing any file. A Node or TypeScript version
  cannot be fixed by choosing another package version, so there is no approval option.
- Node is compared on its major version. When a range needs a later minor, the plan notes the
  minimum version.
- When the `vitest` gate is selected and the project declares `vite`, init checks the Vitest against
  that Vite. A declared Vitest whose release does not declare the project's Vite is `INCOMPATIBLE`,
  such as `vitest` 4.0.18 with `vite` `^8.2.2`, which names the Vitest, the Vite version, and the
  range it supports (`^6.0.0 || ^7.0.0`). Without a declared Vitest, a Vite that no pinned release
  supports, such as `^9.0.0`, is `INCOMPATIBLE`. Vitest minors Ward does not pin are not checked.
  Vitest 4.1.11 needs npm 11.6 or later: Node 22 bundles npm 10.9, which crashes on it
  (npm/cli#9787), so a Vite 8 project on Node 22 must upgrade npm first.
- A SvelteKit project (`@sveltejs/kit` declared) with the `svelte-check` gate needs `svelte-kit sync`
  before the check, because `svelte-check` reads `.svelte-kit/tsconfig.json`. When the `check`
  script runs `svelte-kit sync`, as the SvelteKit template's does, the gate runs that script with
  the package manager (`npm run check`, `pnpm run check`, `yarn run check` or `bun run check`).
  Otherwise the gate runs `svelte-check`, and the plan notes the line to add:
  `"prepare": "svelte-kit sync || echo ''"`. The note does not block init, and init does not edit
  `scripts`. npm does not run the project's own `prepare` script on `npm install`, so run
  `svelte-kit sync` before `ward check` in that setup.
- Ward supports Node 22 and 24. For a project that declares an older Node version, init shows a
  warning that Ward may not work with it. The warning does not stop init or change the files it
  writes, and Bun projects do not get it.

### Generated files

- **`ward-rules.toml`** with the preset and the Node languages the `ward` gate applies. It starts
  with a `# managed-by: ward preset=<id>` marker; see [Lint and style](#lint-and-style).
- **`vitest.config.mjs`** with the coverage reporters, unless the project has its own test config;
  see [Where the minimums live](#where-the-minimums-live).
  A project with no tests fails the test gate until it adds one, because a test gate that passes
  with no tests is misleading.
- **`stryker.config.mjs`** for `stryker` when the project has no `stryker.conf.*`,
  `stryker.config.*`, or `.stryker.conf.*`. It names the test runner, enables the `json`,
  `clear-text`, and `progress` reporters, and sets `thresholds` with `high: 80` and `low: 60`. With
  `strict` it also sets `break: 60`, so Stryker fails below a 60% mutation score. An existing
  Stryker config is kept with its own thresholds.
- These generated configs are ES modules (`.mjs`) in every project and start with a
  `// managed-by: ward preset=<id>` marker. Init rewrites them when you change the preset, and
  never touches a config you wrote.
- **`.gitignore`** gets a Ward-owned section with `.ward/reports/`, created when the file does not
  exist. It lists `coverage/` when a test gate (`vitest`, `jest` or `bun-test`) is configured, and
  `.stryker-tmp/` and `reports/mutation/` with `stryker`. Only the gates init configures add
  their entries.
  `ward-format` skips Git-ignored files, so it does not check these reports.

## Python projects

Init sets up uv, Poetry, and pip projects with the `standard` or `strict` preset. Ward supports Python 3.11 to 3.14; 3.15 waits for mutmut to build on it. PDM and Hatch
projects are not supported yet, and init stops with an error that names the manager.

- Every tool is pinned at an exact version in a PEP 735 `ward` dependency group in
  `pyproject.toml`. A project without `pyproject.toml` gets `requirements-ward.txt`.
- The gates run through the manager: `uv run --group ward`, `poetry run`, or `.venv/bin/` for pip.
  `standard` selects `mypy`, `pytest`, and `coverage` (`minimum = 80` lines), and `ward-format`
  checks formatting.
- Lint comes from Ward's Python rules: `ward-rules.toml` selects them for `"python"` with the
  preset.
- The `coverage` check runs `coverage lcov -o .ward/reports/coverage.lcov` after `pytest`, and Ward
  reads that file (`report`) and compares it with `minimum = 80` (`strict`: `minimum = 85` and
  `minimum-branches = 75`, each measured separately, with branch coverage turned on). The command
  carries no `--fail-under`, and `.coveragerc` holds no `fail_under`.
- `crap` is opt-in and needs `pytest`. `[checks.crap]` reads the same lcov file through `report`,
  after the `coverage` check.
- Ward writes `mypy.ini` and `.coveragerc` only where the project has none. A config the
  project keeps is never changed; a `fail_under` it sets still applies to `coverage lcov`, and Ward
  reads only the `minimum` of `ward.toml`, which the plan says.
- Install runs the manager's sync or install. A failed install restores `pyproject.toml`, the lock
  file, and `requirements-ward.txt`.
- pip needs a `.venv` first (`python -m venv .venv`). When `pyproject.toml` has a `[build-system]`,
  pip also installs the project itself, as `uv sync` and `poetry install` do.
  A pip project with a `src/` layout and no `[build-system]` gets a plan note: pip will not install
  the package, so tests cannot import it until one is added.
- Init refuses Python below 3.11, Poetry below 2.2, and pip below 25.1 (in a project with
  `pyproject.toml`) before it changes any file.
- `strict` adds `mutmut` and selects the strict Ward rules. Strict mypy and branch coverage
  (`minimum = 85` lines and `minimum-branches = 75` of branches, measured separately) apply to Ward's
  own configs, or go on the commands for a project's own. `mutmut` runs in `ci` with a 60% minimum.
- A Django project (a declared `django` package or a `manage.py`) gets `django-stubs` with the mypy
  plugin, `pytest-django` with a Ward `pytest.ini` that names the settings module, and a `django-check`
  gate (`manage.py check --fail-level WARNING`) in both presets. Its import contracts cover every
  top-level package, and each app is a feature under strict. A `[tool.mutmut]` config must name the
  code and tests, because mutmut copies only those paths.
- A FastAPI project adds `httpx` for its test client and the pydantic mypy plugin. A Flask project adds
  `pytest-flask` when it has an app factory (`create_app`), and under strict its blueprints are
  independent features.
- The architecture style (`layered`, `hexagonal` or `clean`) is written to `ward.toml` as layer
  boundaries. The root package comes from `[project] name` under `src/`. Init stops when it finds
  no single root package.

## Android projects

Init recognizes an Android project from the Android Gradle Plugin (`com.android.application` or
`com.android.library`) in the root or a module build script, by plugin id or version-catalog alias.
It keeps the Gradle setup and adds the Android gates.

- **Gates.** `android-lint` runs `lintDebug`, `android-unit-test` runs `testDebugUnitTest`, and
  `android-coverage` runs `createDebugUnitTestCoverageReport` at an 80% minimum (lines only: it takes
  no `minimum-branches`). The JVM `coverage` gate is left out, since an Android root writes no
  `jacocoTestReport` XML report.
- **Modules.** Each Android module script gets the debug unit-test coverage block. An Android module
  applies no JVM plugin, so init writes no JVM quality block into it.
- **Native rules.** The `ward` gate also reads `AndroidManifest.xml` and the XML files under `res/`
  and runs the `ward:android/*` rules of the `standard` and `strict` presets: exported services,
  receivers and content providers without a permission, `android:debuggable`, cleartext traffic,
  `android:allowBackup`, hard-coded text and image views without a content description. They need no
  SDK and no Gradle run, and init writes nothing extra for them. `android-lint` stays for the checks
  that need the compiled platform API.
- **Doctor.** `ward doctor` warns when neither `ANDROID_HOME` nor `ANDROID_SDK_ROOT` names an existing
  directory, and when the Android Gradle Plugin needs a newer JDK or Gradle than the build runs on.

## Swift projects

Init sets up SwiftPM packages and Xcode projects that contain Swift sources, with the `standard` or
`strict` preset. It runs on macOS with Xcode 26.0 or newer. Tuist and XcodeGen projects stop init with an
error that names the generator.

- **Blocking findings.** Init writes nothing and reports these: a machine that is not macOS, an Xcode
  older than 26.0 (or one whose version cannot be read), and an Xcode project with a `Podfile`.
  Move CocoaPods dependencies to Swift Package Manager to use Ward with that project.
- **Lint rules.** The `ward` check applies Ward's Swift rules that the preset selects in
  `ward-rules.toml`, as for Java.
- **Gates.** `ward-format` runs in every profile. A SwiftPM package adds `swift-build` and
  `swift-test`; an Xcode project adds `xcodebuild-test`. Both end with `swift-coverage` in the
  `pre-push` and `ci` profiles, at an 80% minimum under `standard` and 85% under `strict`.
- **Strict.** `strict` selects the same gates with stricter commands, and the strict Ward rules in
  `ward-rules.toml`. It has no mutation gate: no Swift mutation tool is mature enough yet.
- **Proven versions.** CI proves the Swift setup on Xcode 26.0.1, Xcode 26.6, and Xcode 27.0 through
  27.2.

  | Gate | `standard` | `strict` |
  |---|---|---|
  | `swift-build` (SwiftPM) | `swift build --build-tests` | adds `-Xswiftc -warnings-as-errors -Xswiftc -strict-concurrency=complete` |
  | `swift-test` (SwiftPM) | `swift test --enable-code-coverage` | adds the same two compiler flags |
  | `xcodebuild-test` (Xcode) | `xcodebuild test` with coverage | adds `SWIFT_TREAT_WARNINGS_AS_ERRORS=YES SWIFT_STRICT_CONCURRENCY=complete` |
  | `swift-coverage` (SwiftPM) | `swift test --show-codecov-path`, `minimum = 80` | same flags as `swift-test`, `minimum = 85` |

  The project's `Package.swift`, `project.pbxproj` and build settings are never edited; the compiler
  flags and build settings are on the command line only.
- **Xcode scheme and platform.** Init reads the schemes that the project shares, which are the
  `.xcscheme` files in each `xcshareddata/xcschemes` folder. Schemes Xcode creates for each target
  are not counted. One shared scheme is used. With
  several, the wizard asks, or `--scheme <name>` chooses one; `--yes` without `--scheme` fails and
  names the schemes. The test platform is `iOS Simulator`, or `macOS` when every target builds only
  for macOS.
- **Project files.** Ward never edits the project's `Package.swift` or `project.pbxproj`.
- **Configs.** Init writes `.editorconfig` when the project has none. The `.editorconfig` indentation
  follows the project's sources, so Xcode's 4-space templates pass. Files the project keeps are never
  changed.
- **Architecture rules.** Under `strict`, the wizard asks for the style, as `--architecture` answers it.
  Ward writes the layer boundaries to `ward.toml`, checked by `ward:architecture/layers`. It writes no
  Swift package or rules file for them.
- **CI.** The generated workflow runs on `macos-26` and sets up no JDK, Node, or Python for the Swift
  job.

## Gate tools

Init installs no gate tool. A gate whose executable is missing is configured anyway, and the plan
prints a `guidance` line with a link for the executables the catalog knows (none today).
`ward check` reports such a gate as unavailable, and never installs anything.

`--install-tool <gate>[,...]` is still accepted so that existing command lines keep working. It has
no effect, and init logs a warning when it is given.

## Optional generated files

### Quality hooks

Quality hooks are opt-in and separate from agent integrations. `--quality-hooks` adds Ward-managed
sections to `.git/hooks/pre-commit` and `.git/hooks/pre-push`:

- Each section goes after the shebang and before your own logic. It does not replace the hook.
- pre-commit runs `ward check --profile pre-commit --format json` with each staged file as a
  `--path`, so [partial checks](/configuration/gates/#partial-checks) cover the commit's files;
  pre-push runs `ward check --profile pre-push --format json` on the whole project.
- Re-run the option to refresh the sections.
- `--remove-quality-hooks` removes only Ward's marked sections. It keeps your content, executable
  permissions, and other Ward integrations.
- A malformed or duplicate marker is reported as a conflict and left unchanged.

### CI workflow

Without `--ci`, init does not generate a CI workflow. `--ci github` writes
`.github/workflows/ward.yml`, which runs `ward check --profile ci` on pull requests and pushes to
`main`. The workflow:

- installs the Ward release that ran init (`WARD_VERSION`);
- for a Java project, sets up the JDK that runs your build (JDK 25 when init cannot read it), since
  the pinned tools were chosen for that JDK;
- pins the tools the selected gates need;
- fetches full history for `openapi-compat`;
- restores and saves `.ward/cache/vulnerabilities/` around the check when `vulnerabilities` is selected;
- uploads the SARIF report to code scanning for pull requests from the same repository.

In a Node project the workflow sets up Node or Bun instead of Java and installs the dependencies
from the lock file first; see [CI for Node projects](/guides/ci-cd/#node-projects).

The file is Ward-owned, so re-running init refreshes it. An existing workflow at that path without
Ward's marker blocks initialization as a conflict. Gates that need a running application are not set up in the workflow.

### Agent rules

`--agent-rules` writes a Ward-owned section into `AGENTS.md` with the limits the selected gates
enforce: the Ward rule preset for Java and Kotlin, coverage and mutation minimums, and the build policy rules, including the Maven dependency rules.

- For TypeScript it names the `tsc` and test commands, the 70% line coverage minimum of the `coverage` check
  (85% of lines and 75% of branches with `strict`), Stryker (with its 60% minimum under `strict`), and the Ward
  rules in `ward-rules.toml`, and no Java tool.
- For JavaScript it names the same without `tsc`.

- Content outside the section's markers is kept.
- When a rule file is user-owned, the section points to the file instead of quoting preset values.
- Init changes `AGENTS.md` only when you pass `--agent-rules`, and then rewrites the section from the
  preset. Pass it again after tuning rules only if you want the preset values back.

## Choosing projects

Init configures the Maven, Gradle, TypeScript, or JavaScript project that contains the `-C` directory. Started inside a
build module, it configures the aggregator that lists the module, so `ward.toml` lands next to the
aggregator's `pom.xml` or `settings.gradle(.kts)`.

When the `-C` directory is not inside a project init supports, such as the root of a pnpm or Turbo
monorepo whose `package.json` has no JavaScript sources of its own, init looks for projects below it:

- It skips hidden directories and `node_modules`, `target`, `build`, `dist`, and `out`.
- Modules count toward their aggregator instead of being listed.
- With one project found, init configures it and says so.
- With several, the wizard asks which to configure, all checked. Without a terminal, or with `--yes`,
  init stops and lists the `--project` values to pass.

In a Turborepo root, a workspace member with another language's build file, such as a Maven API or
a Python service, is one of these projects, configured with its own toolchain in the same run. See
[Turborepo projects](/guides/turborepo/#members-in-other-languages).
- With none, init stops without changing any file. If the `-C` directory is inside a project of
  another build tool, such as Poetry or Cargo, the error names that build tool and says that init
  supports Maven, Gradle, TypeScript, JavaScript and Python projects. Inside a JavaScript package without
  sources, it reports that no supported project was detected.
- `.js` files inside a Java project, such as `src/main/resources/static/app.js`, belong to that
  project, so they do not make the repository root a JavaScript project.
- A root with a stray script of its own, such as `scripts/release.js`, is a JavaScript project and
  stops discovery. Pass `--project` to choose the projects below it instead.

`--project <dir>` names a project explicitly, relative to `-C`. Repeat it to configure several
projects in one run:

```sh
ward init --project apps/api --project services/billing --preset standard --integration none
```

Each value must be a Maven, Gradle, TypeScript, or JavaScript project root. A module or a subdirectory fails before anything
is planned, and the error names the project to use instead. The answers apply to every selected
project; run init again with a single `--project` to give one project different settings.

## Monorepos

Ward keeps two roots apart:

- The **project root** holds `ward.toml`, the build file, the rule files, and `AGENTS.md`.
- The **repository root**, the Git top-level, holds the files that Git, GitHub, and agent sessions
  read only there.

| File | Single-project repository | Project in `apps/api` |
|---|---|---|
| Quality hooks | `.git/hooks/pre-commit`, `pre-push` | the same files, with a section keyed by `apps/api` |
| CI workflow (`--ci github`) | `.github/workflows/ward.yml` | `.github/workflows/ward-apps-api.yml` |
| Claude Code | `.claude/settings.json`, `.claude/hooks/ward-edit-write` | root `.claude/settings.json`, `.claude/hooks/ward-edit-write-apps-api` |
| OpenCode | `.opencode/...` | root `.opencode/...`, files suffixed `-apps-api` |
| Other agents (Codex, Gemini, Copilot, ...) | `.codex/hooks.json`, ... | the same root files, shared by every project |

The plan shows repository-level files relative to the project root, such as
`modify ../../.git/hooks/pre-commit`. A run that configures several projects lists them once under
**Repository root**. A project whose root is the repository root gets exactly the files it always
did.

The other agents read a single hook file at the repository root, so every project shares one
installation:

- The hook names no project. Ward checks the project whose `ward.toml` is closest above each edited
  file, and at turn end every configured project with changes.
- Edits outside every configured project, such as `apps/web/page.tsx`, run nothing.
- Removing such an integration removes it for every project in the repository.

<Aside title="Upgrading from earlier versions">
Earlier Ward versions wrote these files inside the project, where nothing reads them. After
re-running init, delete them by hand if they exist: `apps/api/.git/hooks/` (only when
`apps/api/.git` holds nothing but that directory), `apps/api/.github/workflows/ward.yml`, and the
Ward files under `apps/api/.claude/`, `apps/api/.opencode/`, and the other agents' directories (such
as `apps/api/.codex/`).
</Aside>

## Wizard tips

- Each question starts with `Step N of M`. The total can grow when an answer adds a follow-up
  question, such as the architecture style under `strict`.
- Press Enter to accept the default shown in brackets: `Enter=1` (`standard`) at the preset question
  and `Enter=layered` at the architecture question.
- Gates whose tool is not installed are marked `[unavailable]`. If you select one anyway, init
  configures it and prints how to make it available.
- The arrow-key menus redraw in place, so your earlier answers stay on screen.

### Keys

| Where | How to answer |
|---|---|
| macOS and Linux terminals | Up/Down to move, Space to toggle, Enter to confirm. `q`, `Q`, or Ctrl+C cancels. |
| Windows, piped input, or no raw terminal mode | Numbered prompts. Pre-selected items show as `[x]`; each number you enter toggles that item, and an empty line accepts the pre-selection. |

For example, after choosing `standard`, entering the number of `coverage` configures every standard
gate except `coverage`.

### Reconfiguring

Run `ward init` again and answer `y` to the overwrite question, or pass `--overwrite`.

- The preset question defaults to `standard`. Ward no longer records a preset in `ward.toml`, so
  re-running init does not preselect the previous preset.
- The gate list starts with the currently enabled gates, so changing one gate takes a couple of key
  presses.
- Integrations, hooks, tools, and, under `strict`, the architecture style are asked as usual.
- If the existing file can't be read, the usual defaults apply.

Answering `n` keeps the file and prints `Kept existing ward.toml. No changes were made.`

See [Gate tools](#gate-tools).

## Review and dry run

Before writing anything, init works out exactly which files it would change. On a terminal it shows
that plan and asks `Proceed? [Y/n]`. Press Enter or answer `y` to apply it. Answer `n`, or end the
input, and nothing changes. The review is skipped with `--yes` and when input is not a terminal.

```console
Ward will make these changes:

  create     ward.toml
  modify     pom.xml
               + jacoco-maven-plugin 0.8.13
               ~ jacoco-maven-plugin 0.8.5 -> 0.8.13 (requires approval)
  create     ward-rules.toml
  keep       config/enforcer-rules.xml  (user-owned, no longer used)
  create     .git/hooks/pre-commit
  create     .claude/settings.json

Proceed? [Y/n]:
```

| Plan entry | Meaning |
|---|---|
| `create`, `modify`, `remove` | Every file init would change, including agent-integration files and Git hooks. |
| `+ plugin version` | A plugin init would add to `pom.xml` or the Gradle build file. |
| `~ plugin old -> new` | A managed plugin version update; `(requires approval)` when it still needs approval. |
| `keep` | A user-owned file init leaves alone. |
| `conflict` | A user-owned file that blocks initialization. Init stops with exit code `2` before writing anything. |

`--dry-run` resolves your answers the same way, prints the plan, and exits with code `0`. It writes
no files, installs nothing, and asks for no compatibility approval:

```console
ward init --dry-run --preset strict --integration none --architecture layered
```

## How questions are answered

Each question is answered by the first of these that applies:

1. The option that answers it, such as `--preset`, `--gate`, `--integration`, `--architecture`,
   or `--quality-hooks`. `--ci` and `--agent-rules` are options only; the wizard does not
   ask for them.
2. Its default, when `--yes` is given: preset `standard` with its gates, integration `none`, no installation,
   no quality hooks, and architecture `layered`. `--yes` never overwrites an existing `ward.toml` (use
   `--overwrite`) and never installs a tool.
3. An answer read from input.

On a terminal, options never hide the questions they don't answer, so
`ward init --integration claude-code` still asks for the preset, gates, and quality hooks.

Without a terminal, for example in CI:

- When `--preset`, `--gate`, or `--integration` is given, init reads nothing. Unanswered questions
  take their defaults, so an open but silent standard input can't make it wait.
- Without options, answers can be piped, for example `printf '1\n1\n\n' | ward init`.

### Missing and invalid answers

- The preset and gate selection is the only required answer. If input ends before it, or it is
  missing in a non-interactive run, init exits with code `2` and suggests `--preset`, `--gate`, or
  `--yes`.
- If input ends at any other question, init uses its default and continues.
- On a terminal, an invalid answer (such as `4` at the preset question, an out-of-range number, or an
  empty gate selection) shows the error and asks again, keeping your earlier answers. The raw-key
  menus stay open after an empty confirmation.
- With piped input, an invalid answer fails immediately with exit code `2` and no changes.

## Troubleshooting with verbose diagnostics

Add `--verbose` to the root command or to `init` to route initialization decisions to stderr. The
diagnostics identify ownership conflicts, applied changes, and rollback outcomes without printing
file contents:

```console
ward --verbose init
ward init --verbose
```

## Exit codes

| Code | Meaning |
|---|---|
| `0` | Initialization succeeded, or `--dry-run` printed the plan. |
| `2` | Invalid usage, or init could not initialize: a conflict, a cancelled or invalid selection, or a missing required answer. |
