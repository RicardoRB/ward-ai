Every check uses `[checks.<name>]` with `command` (string or argument array), optional
`enabled` (default `true`), optional `profiles` (default profile when omitted), and optional `uses`.
`uses` names the built-in tool type that decides how the check's findings are read; when it is
omitted, Ward infers the type from `command`. The `<id>` in the tables below is the type. The command
defines the actual tool invocation. Ward does not install gate tools during `check`.

| Category | ID | Tool | Typical purpose |
|---|---|---|---|
| Build & Tests | `compile` | Maven Compiler / Gradle compilation | Compile the project. |
| | `tests` | JUnit 5 | Run the project's automated tests. |
| | `coverage` | JaCoCo / lcov reports | Fail below a `minimum` line coverage and an optional `minimum-branches`, read by Ward from the tool's report. |
| | `mutation` | PIT | Run mutation testing, optionally with a `minimum` score. |
| Code Quality | `ward` | Ward rules | Check the style and bug rules that `ward-rules.toml` selects, for Java, Kotlin, TypeScript, JavaScript, Python and Swift. |
| | `ward-format` | Ward's native formatter | Check source formatting against `.editorconfig`. Always selected by `ward init`. |
| | `crap` | Ward analysis and a coverage report | Fail functions that are both complex and untested, by their CRAP score. |
| Security | `secrets` | Ward's native secret rules | Detect committed secrets with no tool to install. See [secret detection](/configuration/secrets/). |
| | `vulnerabilities` | Ward and OSV advisories | Match the resolved dependencies against known vulnerabilities. See [vulnerabilities](/configuration/vulnerabilities/). |
| Architecture | `ward` | Ward analysis rules | Run Ward's analysis rules over source syntax trees, with stable `ward:<language>/<rule>` ids, the layer, slice cycle and feature independence rules, and the rules you write in `ward-architecture.toml`, all `ward:architecture/*`. |
| | `build-policy` | Ward's native build policy rules | Pinned plugin versions, no dynamic versions, a minimum build tool version and duplicate dependency declarations in Maven, Gradle, Node and Python build files, and on Maven one version of each dependency and no resolved version below a requested one; see [Build policy rules](/reference/build-policy-rules/). |
| Dependencies & Compliance | `license` | Ward (native) | Licenses of the resolved dependencies against a deny or allow policy, for every toolchain. See [License gate](#license-gate). |
| | `api-compat` | Ward | Compatibility of the public API with the latest release. |
| REST API contract | `openapi-lint` | Ward's OpenAPI rules | Lint the committed OpenAPI spec with every rule, with no tool to install. |
| | `openapi-diff` | Ward breaking-change rules | Breaking changes in uncommitted spec edits. |
| | `openapi-compat` | Ward breaking-change rules | Breaking changes on the branch against `origin/main`. |
| TypeScript & JavaScript | `tsc` | TypeScript compiler | Type-check the project. |
| | `vitest` / `jest` / `bun-test` | Vitest / Jest / Bun test | Run the project's automated tests. |
| | `stryker` | StrykerJS | Run mutation testing, optionally with a `minimum` score. |
| Python | `mypy` | mypy | Type-check the project. |
| | `pytest` | pytest | Run the project's automated tests. |
| | `django-check` | Django system checks | Run `manage.py check` on a Django project. |
| | `mutmut` | mutmut 3 | Run mutation testing, optionally with a `minimum` score. |
| Swift | `swift-build` | Swift build | Compile the SwiftPM package. |
| | `swift-test` | Swift tests | Run the SwiftPM package's tests. |
| | `xcodebuild-test` | Xcode tests | Run an Xcode scheme's tests on an iPhone simulator or the Mac. |
| | `swift-coverage` | llvm-cov / xccov | Fail below a `minimum` line coverage of production code. |
| Android | `android-lint` | Android Lint | Run `lintDebug` through the Gradle wrapper. |
| | `android-unit-test` | Android unit tests | Run `testDebugUnitTest` through the Gradle wrapper. |
| | `android-coverage` | AGP JaCoCo | Fail below a `minimum` line coverage of the debug unit tests. |
| Custom | `command` | — | Run an arbitrary configured project check. |

## Choosing gates

`ward init` offers every gate but selects none unless you choose a preset.

These gates need network access or a comparison baseline, so enable them
deliberately, for example in a CI-only profile with `profiles = ["ci"]`:

- `vulnerabilities`
- `api-compat`

## Moving from the `sonar` gate

Earlier versions of Ward offered a `sonar` gate that ran the SonarQube scanner. It is removed:
`ward init` no longer offers it or writes `sonar-maven-plugin` or the `org.sonarqube` Gradle plugin,
`--gate sonar` and `uses = "sonar"` are an unknown gate, and a check whose command runs
`sonar:sonar` is a plain command check. The plugin entry in your build file is yours to remove.

Ward's own rules, the `crap` gate and the `duplicate-code` rule (see
[duplicate code](/configuration/ward-rules/#duplicate-code)) check code directly, with no server.
Ward does not replace what a SonarQube server keeps: the history of results over time, its
dashboards and the decoration of pull requests. A team that wants those can keep running the scanner
as a command check.

## Quality presets

| Preset | Gates | Minimums |
|---|---|---|
| `standard` | compile, tests, coverage, `ward-format`, and the `ward` check with the standard Java rules of `ward-rules.toml` | 70% line coverage |
| `strict` | `standard` plus the strict Java rules, the `ward` architecture tables, `build-policy` (with the Maven dependency rules), and PIT mutation testing | 85% line, 75% branch, 60% mutation |
| `standard` (TypeScript) | `tsc`, the test runner (`vitest`, `jest` or `bun-test`), and the `ward` check with the standard TypeScript rules of `ward-rules.toml` | 70% line coverage |
| `standard` (JavaScript) | the test runner (`vitest`, `jest` or `bun-test`), and the `ward` check with the standard JavaScript rules of `ward-rules.toml` | 70% line coverage |
| `strict` (TypeScript) | `standard` plus `stryker`, with the strict TypeScript rules of `ward-rules.toml` | 85% line, 75% branch, 60% mutation |
| `strict` (JavaScript) | `standard` plus `stryker`, with the strict JavaScript rules of `ward-rules.toml` | 85% line, 75% branch, 60% mutation |

When Git tracks an OpenAPI spec, both presets add `openapi-lint` and `openapi-diff`, and `strict`
also adds `openapi-compat`. A project whose framework serves HTTP (such as Spring Boot, FastAPI or Express) but has no tracked
spec gets a note asking you to commit one, because the gates have nothing to check without it.

For TypeScript and JavaScript, presets write no rule files under `config/`. Init writes
`ward-rules.toml`, which selects the preset's Ward rules for the project's languages, and adds the
test and mutation tools to `package.json`. It writes their configs when the project has none:
`vitest.config.mjs` with the `text` and `lcov` reporters, and `stryker.config.mjs`. The coverage
minimums are in the `coverage` check of `ward.toml`, not in a test config. Bun checks lines only,
because it does not measure branch coverage. See
[Node projects](/commands/init/#node-projects).

Strict mutation testing can add a lot to check runtime. When `license` is selected, `strict`
writes a license allowlist instead of the GPL/AGPL denylist; see
[License gate](#license-gate).

Presets may write these rule files:

- `ward-rules.toml`, which selects the Ward rules of the preset for the languages of the project, and for `strict` on Java the four `build.*` rules that the `build-policy` check runs, plus `build.dependency-convergence` and `build.require-upper-bound` on Maven (they replace the removed `enforcer` gate; see [moving from the `enforcer` gate](/reference/build-policy-rules/#moving-from-the-enforcer-gate))

No project gets lint tool rule files under `config/`; the Ward rules in `ward-rules.toml` replace them. The files carry a `managed-by: ward` marker. Unmarked user files are never overwritten.

## Build plugins

For Maven-backed gates, `init` picks a version from its embedded Java/Maven compatibility catalog
before adding a missing plugin to `pom.xml`.

- Existing compatible versions are kept.
- Incompatible versions need confirmation, or `--yes` for explicit automation.
- Unknown compatibility, or no compatible version in the catalog, stops init before it writes
  anything and reports how to fix it.

For Gradle projects, the same gate IDs map to Gradle tasks and pinned plugin declarations, in either
the Groovy or the Kotlin build script. See [what init changes](/commands/init/#what-init-changes-in-your-build).

## Standalone tools

Why type checkers, mutation engines, compilers and test runners are not native: [What stays external](/reference/external-tools/).

Ward offers no dynamic scanning (DAST) and no gate for OWASP ZAP. To run ZAP or another scanner, add a
plain `command` check, for example `command = ["zap-baseline.py", "-t", "https://staging.example.com"]`
with `profiles = ["ci"]`. Ward runs it as written and reports only its exit status: it extracts no
findings, gives no install guidance and does not check the target, which you must be authorized to
scan.

- A missing tool is reported as unavailable, and other gates still run.
- `ward init` and `check` never install gate tools.
- When a command contains `--report-path <path>` inside the project, Ward creates the parent
  directory before running it. The command itself never changes.

## TypeScript and JavaScript gates

`tsc`, `vitest`, `jest`, `bun-test`, and `stryker`
run their `command` from the project root, exactly as written, and pass when it exits with code 0.

- Ward does not add flags and does not choose a package manager. Put the runner in the command,
  such as `pnpm exec`, `npx`, `yarn` or `bunx`, so the project's locally installed tool runs.
- For a TypeScript project, `ward init` offers `tsc`, the project's test runner, and `stryker` with
  `strict`, and writes their commands with the package manager's runner. Ward's TypeScript rules run
  in the `ward` check, selected in `ward-rules.toml`; see [Node projects](/commands/init/#node-projects).
- For a Vue, Svelte, or Astro project, the type-check gate is `vue-tsc`, `svelte-check`, or
  `astro-check` instead of `tsc`, because only the framework's checker reads its component files.
  A SvelteKit project whose `check` script runs `svelte-kit sync` gets that script as its
  `svelte-check` command, so the sync runs first.
  The framework comes from the project's declared packages; see
  [Node projects](/commands/init/#node-projects). Angular's type-check gate is `ngc`, which checks
  its templates, and its test gate is `ng-test`. A type-check configuration with no inputs fails
  the gate and names the file.
- For a Vue, Svelte, or Astro project, `stryker` mutates only `src`.
- For a JavaScript project, it offers the same gates without `tsc`.
- Init also offers `stryker`, in the `ci` profile, and `strict` selects it.

```toml
[checks.vitest]
command = ["npx", "vitest", "run", "--coverage"]
profiles = ["pre-push"]

[checks.tsc]
command = ["npx", "tsc", "--noEmit", "--pretty", "false"]
profiles = ["pre-push"]
```

## Turborepo workspaces

A Node workspace root that contains `turbo.json` is a Turborepo project. Its per-source gates run
through turbo from the root, and the repository-wide gates run once:

```toml
[checks.tsc]
command = ["pnpm", "exec", "turbo", "run", "check-types", "--log-prefix=task", "--log-order=grouped", "--continue=always", "--ui=stream"]

```

- `tsc`, test, and `stryker` map to the `check-types`, `test`, and `mutation` tasks. Ward's TypeScript
  rules run from the root `ward` check, so no `lint` task is needed.
  Init writes the missing tasks and each member's script. See
  [Turborepo projects](/guides/turborepo/).
- Findings are read per package. Ward splits the output at turbo's `<package>:<task>: ` prefix,
  parses each block with the gate's parser, and reports the file under the member directory, such as
  `apps/web/src/page.tsx`. Unprefixed output is read as before.
- At a Turborepo root, `minimum` on `stryker` compares the combined score of every member's report.

## Python gates

`mypy`, `pytest`, `coverage`, and `mutmut` run
their `command` from the project root, exactly as written, and pass when it exits with code 0.

- Ward does not add flags and does not choose a package manager. Put the runner in the command,
  such as `uv run` or `poetry run`, so the project's own environment runs the tool.
- When `uses` is omitted, Ward infers the type from the command wherever the tool appears, so
  `coverage report` is `coverage`, `mutmut run` is `mutmut`, and `pytest` is `pytest`, including
  `coverage run -m pytest`.
- `mypy` findings are read from its output; see [structured findings](#structured-findings).

```toml
[checks.mypy]
command = ["uv", "run", "mypy", "-O", "json", "src"]
profiles = ["pre-push"]
```

## Swift gates

`swift-build` and `swift-test` run their `command` from the project
root, exactly as written, and pass when it exits with code 0. `xcodebuild-test` and
`swift-coverage` add the steps below.

- When `uses` is omitted, Ward infers the type from the command wherever the tool appears:
  `swift build` is `swift-build`; `swift test` is `swift-test`; and `xcodebuild test` is
  `xcodebuild-test`. `swift-coverage` is never inferred, so write `uses = "swift-coverage"`.
- `swift-build` and `xcodebuild-test` findings are read from their output; see
  [structured findings](#structured-findings).

```toml
[checks.swift-build]
command = ["swift", "build", "--build-tests"]
profiles = ["default"]

[checks.swift-test]
command = ["swift", "test", "--enable-code-coverage"]
profiles = ["pre-push"]
```

### Xcode tests

An `xcodebuild-test` check names a `platform`: `iOS Simulator` or `macOS`.

```toml
[checks.xcode-tests]
command = ["xcodebuild", "test", "-scheme", "Shop"]
platform = "iOS Simulator"
profiles = ["pre-push"]
```

- For `iOS Simulator`, Ward picks the newest installed iOS runtime and the first iPhone in it by
  name, so `ward.toml` never names a device that another machine or CI image lacks. Ward boots
  the device unless it is already booted, waits until it has finished booting, and appends
  `-destination id=<device>`. It leaves the simulator running, so the next run starts warm. The
  first simulator run on a machine may install CoreSimulator components.
- With no iOS runtime or no iPhone, the gate is an execution error that says how to install one,
  and `xcodebuild` does not run.
- If Ward boots the newest runtime's iPhone and the boot fails, for example because that runtime's
  files are not installed, Ward tries the next newest runtime's iPhone. Simulator lists report a
  runtime as available before its files exist, so the listing alone does not prove it can boot.
  Ward reports the first failure if no iPhone boots.
- For `macOS`, Ward appends `-destination platform=macOS`.
- A command that already has `-destination` runs as written, and `platform` can be left out.
- Every run writes its result bundle to `.ward/reports/xcode/tests.xcresult`: Ward removes the
  bundle an earlier run left there, because `xcodebuild` refuses an existing path, and appends
  `-resultBundlePath`. The gate fails when `xcodebuild` exits with a non-zero code, such as 65 for
  a failing test.

### Swift coverage

A `swift-coverage` check needs `minimum`, the lowest line coverage in percent. After its command
exits with 0, Ward reads the coverage of production code and fails below the minimum.

```toml
# SwiftPM: swift test --show-codecov-path prints where the last coverage run wrote its export.
[checks.coverage]
uses = "swift-coverage"
command = ["swift", "test", "--show-codecov-path"]
minimum = 80
profiles = ["pre-push"]

# Xcode: read the result bundle the xcodebuild-test check wrote.
[checks.xcode-coverage]
uses = "swift-coverage"
command = ["xcrun", "xccov", "view", "--report", "--json", ".ward/reports/xcode/tests.xcresult"]
minimum = 80
profiles = ["pre-push"]
```

- A command that runs `xccov` is read as xccov's JSON report on standard output; test bundles
  (`.xctest`) are left out.
- Any other command is read as SwiftPM: the last line of its output names an llvm-cov export.
  Files under `.build/` or `.ward/`, generated derived sources, and files in a directory named
  `Tests` or ending in `Tests` are left out. Run `swift test --enable-code-coverage` first; a
  failing test writes no export.
- A missing, unreadable or empty report is an execution error, never a pass.
- Coverage of an unconventional layout, such as tests outside a `Tests` directory, counts the test
  files as production code.


## Android gates

`android-lint` and `android-unit-test` run AGP's debug variant tasks, `lintDebug` and
`testDebugUnitTest`, through the project's Gradle wrapper. Ward reads no report for them; the Gradle
exit status decides the gate. They are offered for any project that applies the Android Gradle
Plugin, and `android-coverage` is described below.

What the sources show does not need the SDK: the `ward` gate runs the native `ward:android/*` rules
over `AndroidManifest.xml` and the XML files under `res/<type>/` (`layout`, `menu`, `xml`, `values`,
`drawable`, `navigation` and `color`, with or without qualifiers such as `layout-land`). The rules
follow the ids and documented behavior of Android Lint.

| Rule | Android Lint | Reports |
|---|---|---|
| `ward:android/exported-service` | `ExportedService` | A `service` that is exported and has no `android:permission`. |
| `ward:android/exported-receiver` | `ExportedReceiver` | A `receiver` that is exported and has no `android:permission`. |
| `ward:android/exported-content-provider` | `ExportedContentProvider` | A `provider` with `android:exported="true"` and no `permission`, `readPermission`, `writePermission` or `path-permission`. |
| `ward:android/debuggable-application` | `HardcodedDebugMode` | `android:debuggable="true"` on `application`. |
| `ward:android/cleartext-transport` | `InsecureBaseConfiguration` | `android:usesCleartextTraffic="true"`, and `cleartextTrafficPermitted="true"` on `base-config` or `domain-config`. |
| `ward:android/allow-backup` | `AllowBackup` | `android:allowBackup="true"`, or no `allowBackup`, `fullBackupContent` and `dataExtractionRules`. |
| `ward:android/hardcoded-text` | `HardcodedText` | A literal in `android:text`, `hint`, `title`, `summary` or `label` of a layout, menu, navigation or preference file. |
| `ward:android/unused-resources` | `UnusedResources` | A resource that no XML file and no Java or Kotlin file refers to. |
| `ward:android/missing-content-description` | `ContentDescription` | An `ImageView` or `ImageButton` with neither `android:contentDescription` nor `importantForAccessibility` of `no`. |

A component is exported with `android:exported="true"`, or, for a service or receiver, with an
`intent-filter` and no `exported` attribute. Prefixes are read as written (`android:`, `tools:`),
and `tools:ignore` is not honored: turn a rule off in `ward-rules.toml`. `android-lint` stays for the
checks that need the compiled platform API, such as `NewApi`. 

`ward:android/unused-resources` (Lint `UnusedResources`) reports a resource that nothing refers to: a value of a `values` file (string, color, dimen, bool, integer, style, plurals, array, drawable) or a layout, menu, drawable, color, navigation or XML file. A reference is `@type/name` in any XML file (a style's `parent` and the part of its dotted name before the last dot count) or `R.type.name` in a Java or Kotlin file; a layout also counts as used when its view binding class (`ActivityMainBinding` for `activity_main`) is named. Ward does not follow references through unused files and reports a resource that is read only through `Resources.getIdentifier`.

### Android coverage

An `android-coverage` check needs `minimum`, the lowest line coverage in percent. Its command runs
`createDebugUnitTestCoverageReport`, which writes the debug unit tests' JaCoCo XML report for each
Android module, and Ward sums those reports. Init writes it with a minimum of 80.

```toml
[checks.android-coverage]
uses = "android-coverage"
command = ["./gradlew", "createDebugUnitTestCoverageReport"]
minimum = 80
profiles = ["pre-push", "ci"]
```

- A missing report, or one with no executable lines, is an execution error and never a pass.
- Init turns on the debug unit-test coverage in each Android module script. The `android-lint`
  and `android-unit-test` gates need no block, since they run AGP's own tasks.
- The report path, `build/reports/coverage/test/debug/report.xml`, is assumed and not yet checked
  against a live AGP build.

## Stryker mutation score

Without `minimum`, the `stryker` gate passes or fails on Stryker's exit code alone. With
`minimum = <0-100>`, Ward also reads Stryker's JSON report after a successful run and fails the gate
when the mutation score is below the minimum.

```toml
[checks.stryker]
command = ["npx", "stryker", "run", "--reporters", "clear-text,progress,json"]
minimum = 60
profiles = ["ci"]
```

- The score is detected / valid × 100. Detected mutants were killed or timed out. Valid mutants are
  the detected ones plus those that survived or that no test covers. Ignored, pending, compile-error,
  and runtime-error mutants do not count.
- The command must enable Stryker's `json` reporter. Ward reads the report at Stryker's default
  path, `reports/mutation/mutation.json`.
- At a Turborepo root, Ward reads each planned member's report and compares the combined score. A
  member without a report is skipped; no report at all is an execution error.
- A report that is missing, older than the gate run, unreadable, or without valid mutants is an
  execution error, never a pass. The message says which case applies.
- Stryker's own `thresholds.break` also fails the gate, through Stryker's exit code. The
  `stryker.config.mjs` that init writes with `strict` uses `break: 60` and sets no `minimum`, so the
  threshold lives in one place. Tune it there. Use `minimum` when you keep your own Stryker config
  and want Ward to report the score.

## PIT mutation score

The `mutation` gate accepts the same `minimum`. Without it, the gate passes or fails on PIT's exit
code, which already enforces any `mutationThreshold` in your build. With it, Ward also reads PIT's
XML report after a successful run and fails the gate when the score is below the minimum.

```toml
[checks.mutation]
command = ["./mvnw", "-DoutputFormats=XML,HTML", "pitest:mutationCoverage"]
minimum = 60
profiles = ["ci"]
```

- The score is PIT's own: detected mutations divided by all mutations. It matches what
  `mutationThreshold` would check.
- Ward reads `target/pit-reports/mutations.xml` for Maven and `build/reports/pitest/mutations.xml`
  for Gradle. PIT writes only HTML by default, so enable XML output: `-DoutputFormats=XML,HTML` for
  Maven, or `outputFormats = ['XML', 'HTML']` in the Gradle `pitest` block. Timestamped report
  folders are not read.
- A report that is missing, older than the gate run, unreadable, or without mutations is an
  execution error, never a pass.

## mutmut mutation score

The `mutmut` gate accepts the same `minimum`. Run mutmut 3 with `mutmut run`. Without `minimum`, the
gate passes or fails on mutmut's exit code alone. With it, Ward reads mutmut's per-file results
after a successful run and fails the gate when the score is below the minimum.

```toml
[checks.mutmut]
command = ["uv", "run", "mutmut", "run"]
minimum = 60
profiles = ["ci"]
```

- The score counts detected mutants (killed, timed out, or caught by the type checker) divided by
  valid mutants (detected, survived, or with no tests). Skipped, not checked, suspicious, and
  interrupted mutants do not count.
- Ward reads the `.meta` files under `mutants/`, which mutmut 3 writes in the project root. It
  decodes only the exit codes, so a mutmut layout change can make the results unreadable.
- Results that are missing, older than the gate run, unparseable, or without valid mutants are an
  execution error, never a pass. mutmut always writes these results under `mutants/`, so Ward
  reads them there.
- mutmut's results for source files that were deleted keep counting until mutmut rewrites them.

## Format gate

`uses = "ward-format"` runs Ward's native formatter over the project's engine-language sources and
reports each file it would change. It is a `FAST` gate, so it runs on every edit.

```toml
[checks.ward-format]
uses = "ward-format"
profiles = ["default", "edit", "pre-push", "ci"]
```

The gate needs no `command`. It reports one error per unformatted file, at the first line that
differs, with the rule `ward-format` and the message `file is not formatted`. A file the formatter
refuses, or one whose `.editorconfig` is invalid, is an execution error, never a pass. The gate never
changes a file: run [`ward format`](/commands/format/) to fix the reported files.

On a partial run, such as the `edit` profile after one file changed, the gate checks only the changed
files when its `paths` table matches them, as the analysis gate does. Results for files that are
already formatted are cached by content and settings, so unchanged files cost nothing on the next run.

## Coverage gate

The `coverage` check reads a coverage report and fails below the minimums in `ward.toml`. The tool
measures; Ward decides. Init writes no minimum into `pom.xml`, the Gradle build, a test runner config,
`bunfig.toml` or `.coveragerc`.

```toml
[checks.coverage]
profiles = ["pre-push", "ci"]
command = "./mvnw jacoco:report"   # optional
minimum = 85                        # required: line coverage in percent, 0 to 100
minimum-branches = 75               # optional: branch coverage in percent
report = "target/site/jacoco/jacoco.xml"   # optional: a path or an array of paths
```

- `minimum` is required; a `coverage` check without it is a configuration error that names the check
  (exit code 2). `minimum-branches` is accepted only here; every other type, `swift-coverage` and
  `android-coverage` included, rejects it.
- With a `command`, Ward runs it, and reads the report only when it exits with code 0. Without one
  (`uses = "coverage"`), Ward starts no process and reads the reports an earlier check wrote, which is
  how Node projects work: the check follows the `vitest`, `jest` or `bun-test` gate. A command that
  contains `jacoco:report`, `jacocoTestReport` or `coverage lcov` is inferred as a `coverage` check;
  `jacoco:check`, `jacocoTestCoverageVerification` and `coverage report` are plain command checks.
- Ward reads JaCoCo XML and lcov, choosing the format from the content of the file. A JaCoCo line or
  branch is covered as JaCoCo counts it; an lcov line is covered when its `DA` hits are above 0, and
  a branch when its `BRDA` taken count is above 0.
- Line and branch coverage are the covered over the coverable count, summed over every file of every
  report, so a multi-module Maven or Gradle build is checked as one total (a high-coverage module can
  hide a low one). A line is covered when any report covers it.
- Without `report`, Ward reads the build tool's default report in the project root and in every
  module directory: `target/site/jacoco/jacoco.xml` (Maven),
  `build/reports/jacoco/test/jacocoTestReport.xml` (Gradle), `coverage/lcov.info` (Node, Turborepo
  members included) and `coverage.lcov` (Python; init sets `report = ".ward/reports/coverage.lcov"`).
  A path outside the project is a configuration error.
- The gate ends with an execution error, never a pass, when no report exists (it says to run the test
  gate first), a file is neither JaCoCo XML nor lcov, an lcov file is truncated, there is no coverable
  line, `minimum-branches` is set and no report records branches (Bun, or coverage.py without
  `branch = True`), a check with a command finds no report written after the command started, or a
  check without one finds a report older than a source file it names. A report that records branches
  and has none passes the branch minimum.
- Vitest and coverage.py list only the files the tests load, so a file no test imports does not lower
  the measured number; JaCoCo analyzes every class.
- Angular (`ng test`) gets no `coverage` check from init. Its own `angular.json` or `karma.conf.js`
  sets any threshold. Add `[checks.coverage]` with `uses = "coverage"`, `minimum` and the `report`
  path of the lcov file it writes to enforce a minimum from `ward.toml`.
- A threshold in a config the project owns (a Jest `coverageThreshold`, a Vitest threshold, a
  `bunfig.toml` threshold, a `fail_under`) keeps applying to its tool. Ward does not read or edit it.

What `ward init` writes, by toolchain: the preset sets `minimum` (70 for Maven, Gradle and Node
`standard`, 80 for Python `standard`, and 85 with `minimum-branches = 75` for `strict`; a custom Maven
or Gradle selection writes 80, a custom Node selection 70; Bun's `strict` has no
`minimum-branches`). Maven gets the JaCoCo plugin with `prepare-agent` and `report` executions and no
`rules`; Gradle gets the XML report setting; Vitest gets a Ward-owned config with the `lcov`
reporter, Jest and Bun get reporter flags on their command where needed.

## CRAP gate

`uses = "crap"` scores every function with the CRAP metric (Change Risk Anti-Patterns) and fails the
functions above a limit. A function that is complex and untested scores high, even when the rest of
the project is well covered, which neither the complexity rules nor the `coverage` minimum catch:

```
CRAP = complexity^2 * (1 - coverage)^3 + complexity
```

```toml
[checks.coverage]
profiles = ["ci"]
command = "./mvnw -DskipTests package jacoco:report"
minimum = 70

[checks.crap]
uses = "crap"
profiles = ["ci"]
max = 30
```

The gate runs no tests and no process. It reads the per-line coverage report that the coverage or
test check wrote, so declare it after that check: checks run in the order `ward.toml` declares them.

- **Complexity** is the value that Ward's complexity rule of the language computes for the function:
  `ward:java/cyclomatic-complexity`, `ward:kotlin/cyclomatic-complexity`,
  `ward:typescript/complexity`, `ward:javascript/complexity`, `ward:python/complexity` and
  `ward:swift/complexity`. It does not matter whether the rule is selected in `ward-rules.toml` or
  what limit it has.
- **Coverage** of a function is its covered lines over its coverable lines, from the first to the
  last line of its declaration. A line counts only for the innermost function that contains it, so a
  nested function does not count for its outer function, while a lambda counts for its method.
- A function with no coverable line in the reports, such as an interface method, or in a file that
  no report names, is scored from its complexity alone.

`max` is an integer of at least 1, 30 by default, the threshold of the original metric. A function
fails when its score is above `max`; a score equal to it passes. Each failing function is one error
finding at its declaration, for example `CRAP score 42 is above 30 (complexity 6, coverage 0%)`, and
the summary states how many functions were scored and how many are above the limit.

### Coverage reports

The gate reads JaCoCo XML (Java, Kotlin, Android) and lcov (TypeScript, JavaScript, Python, SwiftPM),
choosing the format from the content of the file. `report` is one project-relative path or an array
of them, and a path outside the project is a configuration error. Without `report`, Ward reads the
default report of the project's build tool, in the project root and in every module directory below
it:

| Build tool | Default report |
|---|---|
| Maven | `target/site/jacoco/jacoco.xml` |
| Gradle | `build/reports/jacoco/test/jacocoTestReport.xml` |
| npm, pnpm, Yarn, Bun | `coverage/lcov.info` |
| uv, Poetry, PDM, Hatch, pip | `coverage.lcov` |
| SwiftPM, Xcode | none: set `report` |

When several reports name the same line, the line is covered when any of them marks it covered. An
lcov path is taken as absolute, or resolved against the project root and then against each directory
from the report's own directory up to the root. A JaCoCo entry matches the source file whose path ends
with its package and file name, preferring the file in the module that holds the report.

To make each tool write the report:

- **Maven:** the `jacoco-maven-plugin` goal `prepare-agent` before the tests and `report` after them;
  the XML report is written by default.
- **Gradle:** the `jacoco` plugin with `jacocoTestReport { reports { xml.required = true } }`, run
  after `test`.
- **Vitest:** `coverage: { reporter: ['lcov'], include: ['src/**'] }` and `vitest run --coverage`.
  **Jest:** `collectCoverageFrom` and `jest --coverage`, whose default reporters include `lcov`.
  List the source files in `include` or `collectCoverageFrom`, or the files no test loads are absent
  from the report.
- **pytest:** `pytest --cov=<package> --cov-report=lcov`, which writes `coverage.lcov`.
- **SwiftPM:** `swift test --enable-code-coverage`, then export the profile with
  `xcrun llvm-cov export -format=lcov` to a file and name it in `report`. Xcode projects that measure
  coverage with `xccov` have no lcov export and are not read.

### What `ward init` writes for `crap`

`crap` is opt-in: no preset selects it, and `ward init --preset standard --gate crap` adds it. It
needs the gate that produces the coverage data (`coverage` for Maven and Gradle, the test gate for
Node, `pytest` for Python); init stops with exit code 2 and writes no file when that gate is missing.
Init writes `[checks.crap]` after the `coverage` check, in the `pre-push` and `ci` profiles. The
`coverage` check already makes each tool write the report that `crap` reads (the JaCoCo XML report for
Maven and Gradle, `coverage/lcov.info` for Vitest, Jest and Bun, `.ward/reports/coverage.lcov` for
Python), so `crap` adds no report-writing of its own.

Init does not offer `crap` for Swift, Android and Angular (`ng test`) projects, because it cannot
make their coverage tool write a report at a known path. Add the table by hand with a `report`: for
SwiftPM the `llvm-cov export -format=lcov` file above, for Android the JaCoCo XML report of your
coverage task, and for Angular the lcov file that your Karma or Vitest reporter writes.

### Reports that cannot be used

The gate never passes on a report it cannot trust. It ends with an execution error that names the file
and says the coverage check must run first when:

- no report is found, or a configured `report` does not exist;
- a report is neither JaCoCo XML nor lcov, or is truncated;
- the reports name no source file of the project;
- a source file that a report names was modified after the report was written, which usually means the
  tests did not run since the edit. A fresh checkout can also trigger it, so run the coverage check
  first;
- a source file that a report names cannot be parsed.

The gate is opt-in: no preset selects it. It does not honor `exclude-paths` of `ward-rules.toml` and
does not run on partial (edit-hook) runs.

## Analysis gate

`ward` runs Ward's own analysis rules over the project's source files. It needs no `command`:

```toml
[checks.ward]
enabled = true
uses = "ward"
profiles = ["pre-push", "ci"]
```

Each rule has a stable id of the form `ward:<language>/<rule>`. A rule runs only when the language
frontend provides the capability the rule needs. A rule whose capability is missing is reported as
not run, and the gate is unavailable rather than passed. A file that cannot be parsed or a rule that
fails is an execution error, and the gate does not pass. The report then names each file or rule
that failed, after the findings. Findings appear in the same check report, JSON and SARIF output as
the other gates.

The gate skips hidden folders, build output (`target`, `build`, `dist`, `node_modules`, `mutants`),
and Java or Kotlin files under a `src/<set>/resources` folder, which Maven and Gradle never compile.

Select rules with `rules`. Unknown rule ids and unknown keys are configuration errors:

```toml
[checks.ward]
uses = "ward"
rules = ["ward:java/method-length"]
```

To choose rules by preset, language or category, tune their limits and severity, and leave paths
out, create a [`ward-rules.toml`](/configuration/ward-rules/). When that file exists, the `rules`
list in `ward.toml` is a configuration error. `rules-file = "config/ward-rules.toml"` points the
check at another file inside the project.

### Java dependency edges

The `ward` gate also resolves Java imports and type names to the project's own source files. An
`import shop.domain.Price;`, a same-package name, a fully qualified name or a nested type each
produce an edge to the file that declares the type, with Java's name lookup order. Ward reads the
source roots of each Maven and Gradle module from its build file and does not run the build. Types
from the JDK or from jars produce no edge.

Names in the source are enough for most code. A type that only type inference shows, such as the
type of a `var`, of a chained call or of a lambda parameter, needs the classpath of the project.
Name a file that lists the classpath entries with `java-classpath`, relative to the project root.
The file holds entries separated by the platform path separator or by newlines. Ward reads the file
and does not write it. A missing or unreadable file is a configuration error that names the key and
the file:

```toml
[checks.ward]
uses = "ward"
java-classpath = "target/classpath.txt"
```

Write the file with the build tool, for example with Maven:

```bash
./mvnw dependency:build-classpath -Dmdep.outputFile=target/classpath.txt
```

With Gradle, add a task to the build script that writes the test compile classpath:

```kotlin
tasks.register("writeClasspath") {
    doLast {
        layout.buildDirectory.file("classpath.txt").get().asFile
            .writeText(sourceSets.test.get().compileClasspath.asPath)
    }
}
```

Then run `./gradlew writeClasspath` and set `java-classpath = "build/classpath.txt"`. Binding
resolution uses Eclipse JDT, which is part of the `ward` binary. It parses every Java file on each
run, so it is slower than the default; the result cache still reuses unchanged results.

The same classpath file gives the type-aware rules their library types. Ward reads the class files
of the jars and directories it lists, and the JDK's `lib/modules` image, without starting `javac`
or any other process; an entry that is missing or unreadable makes its types unknown, not an error.
It indexes each jar once and keeps the index under `.ward/cache/types/`, named by the SHA-256 of the
jar's content.

### Result cache

The `ward` gate keeps each source file's results in `.ward/cache/analysis/`, and reuses them on the
next run when the file, the selected rules with their options and severity, and the Ward version are
all unchanged. Cached results
match a full run exactly. A file that failed to parse or a rule that failed is never cached, so a
failure is always analyzed again. The directory is git-ignored. Delete `.ward/cache/` to force a full
run; nothing else depends on it. Entries are not pruned yet, so the directory grows as files change.

The same directory also holds each file's summary (its exports, imports and declared names) and a
reverse-dependency index, which the gate rewrites after every clean run. A rule that reads other files
keys each file on the names of the files it imports and the files that import it, so an edit
analyzes again only the files around the change. Deleting `.ward/cache/` still forces a full run.

### Java rules

Ward ships thirteen Java rules. They are the structural checks of the strict
preset, so a Java project can run them in the same pass as the rest of its gates:

| Rule | Limit or pattern |
|---|---|
| `ward:java/file-length` | more than 500 lines |
| `ward:java/method-length` | method body over 60 lines |
| `ward:java/parameter-count` | more than 5 parameters |
| `ward:java/cyclomatic-complexity` | above 10 |
| `ward:java/cognitive-complexity` | above 15 |
| `ward:java/star-import` | any `.*` import |
| `ward:java/unused-import` | a simple name used nowhere else, including Javadoc |
| `ward:java/missing-javadoc` | public types and methods without Javadoc |
| `ward:java/type-name` | `^[A-Z][a-zA-Z0-9]*$` |
| `ward:java/method-name` | `^[a-z][a-zA-Z0-9]*$` |
| `ward:java/member-name` | non-static fields matching `^[a-z][a-zA-Z0-9]*$` |
| `ward:java/parameter-name` | `^[a-z][a-zA-Z0-9]*$` |
| `ward:java/local-variable-name` | `^[a-z][a-zA-Z0-9]*$` |

Differences from the upstream checks, by construction:

- `unused-import` is textual. It does not resolve names, so a fully qualified use still counts as
  unused and a same-named identifier from another package counts as a use.
- `missing-javadoc` checks only the comment immediately before a declaration. It skips `@Override`
  methods, does not check interface members, and skips public types nested in a non-public type, as
  the upstream scope does.
- `method-length` and the complexity rules measure methods only. Constructor bodies are not
  measured by `method-length`, and nested classes and lambdas count toward their enclosing method.
- `cognitive-complexity` follows the published definition in a simplified form: each `&&` and `||`
  adds one, an `else if` chain does not nest, and a final `else` adds one.
- Java comments are read from the syntax tree. Comments that Ward's parser cannot attach to a
  declaration are not documentation for `missing-javadoc`.

Rule ids and limits are stable across releases. A rule whose id changes is published under a new
id.

### Data-flow rules

Data-flow rules read the control flow of each function and how it uses its local variables and
parameters. They run in the `ward` gate with the other rules:

| Rule | Reports |
|---|---|
| `ward:java/unused-assignment` | a write to a local variable or parameter that no read can observe |
| `ward:typescript/unused-assignment` | the same check, for TypeScript |
| `ward:javascript/unused-assignment` | the same check, for JavaScript |

Differences from the upstream check, by construction:

- A write is reported when a later write can replace it on some path, or when it is an assignment to
  a name that is not exempt. The names `_`, and names that start with `ignored` or `unused`, are
  exempt for the last assignment only. An initializer or an incoming parameter value that nothing
  replaces is not reported, as upstream does.
- A variable that a nested function, lambda or arrow function reads or writes is never reported.
- Fields, object properties and array elements are not tracked, and neither are variables of another
  function.
- The analysis is intraprocedural. It does not follow values across calls and does not compute
  constant values.
- A `finally` block is entered from every exit of its `try`, so a value can seem to reach a read
  along a path that the language cannot take. Such a write is not reported.

### Scope rules

Rules with the `SCOPES` capability know which declaration each name refers to. Ward builds the
scopes of a file once, whatever the number of rules that read them, and follows each language's own
scoping rules:

| Language | Scoping rules the analysis follows |
|---|---|
| Python | local, enclosing function, module, built-in (LEGB); `global` and `nonlocal`; class bodies that their methods skip; comprehension scopes; `del`; names in a literal `__all__` are exported |
| JavaScript and TypeScript | `var` and function declarations hoisted to the function; `let`, `const` and classes in their block with a temporal dead zone; `catch` and parameter scopes; type-only imports and declarations in TypeScript |
| Java and Kotlin | members, locals, parameters, lambdas, inner and anonymous classes, static imports; Kotlin companion objects and `it` |
| Swift | members, locals, closures, `guard let` and `if let` bindings, `switch` pattern bindings |

A name that no scope declares and no built-in provides is *unresolved*. Where the analysis cannot
see every name, it marks the scope *open*, and a rule that reports undefined names stays silent in
it. A scope is open after a Python `from m import *`, a call of `exec`, `eval`, `locals` or `vars`,
a JavaScript `with` or `eval`, a Java static wildcard import, and in a class that extends or
implements something, an enum, a Kotlin extension function or receiver lambda, and a Swift
extension. A Java, Kotlin or Swift name that starts with an upper-case letter, or that a file of
the same package or module declares, is also left alone, because the type may come from there.

Built-in names are the Python builtins, the globals of the `es2024` JavaScript environment plus
those of `browser` and `node` by default, `java.lang`, the Kotlin standard library's default
imports and the Swift standard library. A rule that reads JavaScript or TypeScript globals declares
an `env` option, a list of environments added to `es2024`.

A name imported from a project module resolves through the dependency graph to the file and the
symbol it declares; an import from outside the project stays an import binding with no
declaration.

Ward ships no rule on this capability yet. The rules of the roadmap for undefined names, unused
variables, redefinitions and shadowing build on it.

## Kotlin structural rules

The `ward` gate runs seven Kotlin structural rules for `.kt` files, including files in Gradle Kotlin
modules. They read the syntax tree from the ANTLR Kotlin frontend and use the same limits as the
Java size and naming rules.

| Rule | Limit or pattern |
|---|---|
| `ward:kotlin/file-length` | more than 500 lines |
| `ward:kotlin/function-length` | function body over 60 lines |
| `ward:kotlin/parameter-count` | more than 5 value parameters |
| `ward:kotlin/cyclomatic-complexity` | above 10 |
| `ward:kotlin/cognitive-complexity` | cognitive complexity above 15 |
| `ward:kotlin/type-name` | `^[A-Z][a-zA-Z0-9]*$` for classes, interfaces, objects and enums |
| `ward:kotlin/function-name` | `^[a-z][a-zA-Z0-9]*$` |

Differences from the Java rules, by construction:

- Cyclomatic complexity counts `if` expressions, each `when` entry (an `else` entry counts too), `for`,
  `while`, `do`, `catch`, each `&&` and `||`. The elvis operator `?:` does not count.
- Cognitive complexity adds one per `if`, `when`, `for`, `while`, `do` and `catch`, plus its nesting
  depth, and one per `&&` and `||`. An `else` adds one. An `else if` is not scored as nested, so the
  chain is checked at the same depth. The rule is not compared with the Java rule's output.
- `function-length` measures the function body, from its opening brace to its closing brace.
  Expression-bodied functions are measured by the same limit.

## Python structural rules

The `ward` gate runs five Python structural rules for `.py` files. They read the syntax tree from
the ANTLR Python frontend and use fixed limits. Init selects the Python rules of the preset in
`ward-rules.toml`.

| Rule | Limit | Severity |
|---|---|---|
| `ward:python/function-length` | more than 60 lines in a function, from the `def` line | error |
| `ward:python/parameter-count` | more than 5 parameters; `self` and `cls` of a method are not counted | error |
| `ward:python/complexity` | complexity above 10 | error |
| `ward:python/file-length` | more than 500 lines in a module | error |
| `ward:python/naming` | functions and variables `snake_case`, classes `CapWords`; dunder names skipped | warning |

Complexity is one plus the decision points in a function: `if`, `elif`, `while`, `for`, `except`,
`match` cases, comprehension `for` and `if` clauses, each `and` and `or`, and conditional
expressions. Nested functions, classes and lambdas are measured on their own.

Enable the rules by naming them in `ward.toml`:

```toml
[checks.ward]
uses = "ward"
rules = [
  "ward:python/function-length",
  "ward:python/parameter-count",
  "ward:python/complexity",
  "ward:python/file-length",
  "ward:python/naming",
]
```

A file with a syntax error is not checked by these rules. It is reported as an execution error, and
the gate does not pass. Limits are not keys of the check: a `ward` check accepts only `uses`,
`enabled`, `profiles`, `rules`, `rules-file`, `architecture-file`, `java-classpath`, `layers`,
`cycles` and `independence`. Tune a limit in [`ward-rules.toml`](/configuration/ward-rules/).

## Which rule goes in which file

| Rule | File | Written by |
|---|---|---|
| Style, bug and security rules, their options and severity (`ward:<language>/*`) | [`ward-rules.toml`](/configuration/ward-rules/) | `ward init`, `ward rules` |
| `ward:architecture/layers`, `/cycles`, `/independence` | the `layers`, `cycles` and `independence` tables of the `ward` check in `ward.toml` | `ward init` |
| `ward:architecture/dependencies`, `/naming`, `/location`: your own architecture rules | [`ward-architecture.toml`](/configuration/ward-architecture/) | you |

`ward.toml` does not accept the rules of `ward-architecture.toml`: an `architecture` table under the
`ward` check is an unknown key. `architecture-file` in the check points at another path for the
file, as `rules-file` does for `ward-rules.toml`.

## Layer boundaries

Each `[[checks.ward.layers]]` table forbids dependencies between layers. A file is in a layer when a
directory in its path has the layer's name, and the rule `ward:architecture/layers` reports every
dependency from a `from` layer to a `forbidden` layer, at the import that creates it:

```toml
[checks.ward]
uses = "ward"

[[checks.ward.layers]]
from = ["domain", "application"]
forbidden = ["adapter", "infrastructure"]
```

Both lists are non-empty and name plain directory names. The rule covers Java, Kotlin, Python,
TypeScript, JavaScript and Swift (Swift folder names compare ignoring case; Swift edges exist when
the folder is a SwiftPM or Xcode project). A Kotlin file importing a Java file of a forbidden layer,
and the reverse, are both reported. Java, Kotlin and Swift test sources are not checked. `ward init` writes this table for the
chosen style.

The table is a shorthand of a `must-not-depend-on` rule of `ward-architecture.toml` that selects
`directories = [<from>]` with `exclude-paths` for the Java and Swift test folders, and forbids
`directories = [<forbidden>]`; both report the same files and lines. The table keeps the rule id
`ward:architecture/layers` and its message.

## Slice cycles and feature independence

`[checks.ward.cycles]` names the source roots whose slices must not form a dependency cycle. A slice
is the first directory below the longest root that holds a file. A file directly in a root, or
outside every root, belongs to no slice. The rule `ward:architecture/cycles` reports each group of
two or more slices that depend on each other in a cycle, once, at an import that leaves the group's
alphabetically first slice. Its path lists one step per slice dependency of the shortest cycle
through that slice. Cycles inside one slice are not reported, so a file cycle within one folder is
not a finding under this rule.

```toml
[checks.ward.cycles]
roots = ["src/main/java/com/acme"]
```

`[[checks.ward.independence]]` lists module directories that must not depend on each other. The rule
`ward:architecture/independence` reports every import from a file in one listed module to a file in
another listed module of the same table, at the line of the import. Code that both modules share
outside the list is allowed.

```toml
[[checks.ward.independence]]
modules = ["shop/orders", "shop/billing"]
```

A table of modules that are not nested equals one `must-not-depend-on` rule per module in
`ward-architecture.toml`, selecting `paths = ["<module>/**"]` and forbidding the paths of the other
modules. Nested modules, where the longest module wins, and `cycles` have no longhand.

Both lists are validated: `roots` is non-empty and holds project-relative directories, and each
`modules` list has at least two entries. Both rules read the dependency edges of every language the
engine resolves, Kotlin included. `ward init --preset strict` writes these tables. Init
writes no external cycle or independence rule.

## Swift structural rules

The `ward` gate runs six Swift structural rules for `.swift` files. They read the syntax tree from
the ANTLR Swift frontend and use fixed limits. They are the Swift style and lint checks; no external linter gate runs beside them.

| Rule | Limit | Severity |
|---|---|---|
| `ward:swift/function-length` | more than 60 lines in a function, method or initializer, from the declaration line | error |
| `ward:swift/parameter-count` | more than 5 parameters; defaulted and variadic parameters count | error |
| `ward:swift/complexity` | complexity above 10 | error |
| `ward:swift/file-length` | more than 500 lines in a file | error |
| `ward:swift/type-body-length` | more than 300 lines in a `struct`, `class`, `protocol`, `extension` or enum, from the declaration line | error |
| `ward:swift/naming` | types `UpperCamelCase`; functions, variables, constants and enum cases `lowerCamelCase`; leading underscores and backticks ignored | warning |

Complexity is one plus the decision points of a function or initializer: `if`, `guard`, `else if`,
`for ... in`, `while`, `repeat ... while`, each `catch`, each `case` label, each `?:`, and each `&&`
and `||` operator. An `else` adds nothing. Closures are not measured as units: their decisions are
left out of the enclosing function, as nested functions are, but a closure over the limit is not
reported on its own.

Enable the rules by naming them in `ward.toml`:

```toml
[checks.ward]
uses = "ward"
rules = [
  "ward:swift/function-length",
  "ward:swift/parameter-count",
  "ward:swift/complexity",
  "ward:swift/file-length",
  "ward:swift/type-body-length",
  "ward:swift/naming",
]
```

The Swift frontend uses a Ward-owned Swift 5 grammar, not the Tree-sitter grammar. A file with a
syntax error is not checked by these rules; it is reported as an execution error and the gate does
not pass. To see which sources the grammar parses, compare your files with the parse report in the
Ward repository (`ward-lang-swift/src/test/resources/corpus/parse-report.txt`). At the time of
writing, the parse report lists `func run() async {` (first error at 6:18) and a freestanding macro
declaration (2:8) as errors; the cause is not analyzed here. Limits are tuned in
[`ward-rules.toml`](/configuration/ward-rules/), as for the Python rules.

## License gate

The `license` gate is native: it reads the packages of the [dependency inventory](#structured-findings)
and each package's declared license from local files, normalizes it to an SPDX expression, and
checks it against a policy. It runs for Maven, Gradle, Node, Python and Swift projects, takes no
`command`, and never uses the network or runs your build tool. A `command` on a `license` check is a
configuration error.

```toml
[checks.license]
uses = "license"
profiles = ["pre-push", "ci"]
deny = ["GPL-*", "AGPL-*"]        # the default; or allow = ["Apache-2.0", "MIT"]
exceptions = ["Classpath-exception-2.0"]
scopes = ["runtime", "provided"]  # default: every scope
unknown = "fail"                  # or "warn"
```

| Key | Meaning |
|---|---|
| `deny` | SPDX identifiers, each optionally ending in `*` for a family. The default is `["GPL-*", "AGPL-*"]`; `GPL-*` does not match `LGPL-*`. |
| `allow` | An allowlist in the same notation. Set `allow` or `deny`, not both. |
| `exceptions` | `WITH` exceptions that waive a denied license (default `["Classpath-exception-2.0"]`); a deny policy only. |
| `scopes` | Inventory scopes that are checked: `runtime`, `provided`, `test`, `development`. Default: all. |
| `unknown` | `"fail"` (default) or `"warn"`: the severity of a license Ward cannot find or recognize. |

Where each ecosystem's license is read:

- **Maven and Gradle:** the POM in `~/.m2/repository` or the Gradle module cache, with the license of
  the `<parent>` POM when a POM has none.
- **Node:** `package.json` in `node_modules` (hoisted, nested or the `.pnpm` store); the version must
  match the lockfile's.
- **Python:** `License-Expression`, `License` or `License ::` classifiers in the `.dist-info` of the
  project's virtual environment (`.venv`, `venv` or `VIRTUAL_ENV`).
- **Swift:** `Package.swift` declares no license, so Ward matches the `LICENSE` or `COPYING` file of the
  package checkout (`.build/checkouts`) against the bundled license texts.

A package that is not installed locally, or whose license Ward does not recognize, is a
`ward:license/unknown` finding, never an allowed one: install the dependencies before the gate runs,
or set `unknown = "warn"`. Several declared licenses are alternatives, and an `OR` expression passes
when one choice is allowed. The findings are `ward:license/denied`, `ward:license/not-allowed` and
`ward:license/unknown`. If the dependencies cannot be resolved the gate reports an execution error
instead of passing. `ward init --preset strict` writes an `allow` list of Apache-2.0, MIT,
BSD-2-Clause, BSD-3-Clause, ISC, EPL-1.0, EPL-2.0 and CC0-1.0. See also
[`ward sbom` and `ward licenses`](/commands/sbom/).

## API compatibility

`api-compat` compares the public API of the project's main sources in the working tree with the
public API of the same sources at an earlier Git revision, and reports each incompatible change.
For Java it is a Ward check: it runs no build, no external tool and no network access, reads the
baseline from Git objects (nothing is checked out), and works the same for Maven and Gradle.

```toml
[checks.api-compat]
uses = "api-compat"
profiles = ["ci"]
base = "v1.4.0"             # optional: a Git ref; default is the latest release tag
include = ["com.acme.api"]  # optional: package prefixes that limit the API
modules = ["core", "api"]   # optional: module directories to compare; default every module
```

- **Baseline.** `base` names a Git ref. Without it, the baseline is the highest release tag
  reachable from `HEAD` (`v1.2.3` or `1.2`, any further numeric segments, no suffix), other than a
  tag that points at `HEAD`. Pre-release tags such as `v1.0.0-rc1` are never a baseline. Ward never
  fetches: CI needs full history and tags (`fetch-depth: 0`), which init's workflow sets.
- **Scope.** Types in the main source roots, read from `pom.xml` or the Gradle script at each
  revision. Test sources are not API. `include` limits the API to types whose qualified name starts
  with one of the package prefixes. A top-level Kotlin declaration belongs to the type
  `<package>.<top-level>`, so `include = ["com.acme.api"]` covers it.
- **Multi-module builds.** Ward finds the modules at the baseline and in the working tree: Maven
  `<modules>` (followed recursively, profile modules included) and the projects of a Gradle
  `include("a", ":b:c")` in `settings.gradle(.kts)`, and reads each module's source roots from its
  own build file. All modules are read together, so a type that extends a type of another module
  still resolves. A finding in a module other than the root starts with `[<module>]`. A module that
  is new has no baseline and causes no finding. A module that was removed or whose directory was
  renamed removes its API, so its types are reported `type-removed`. A type that keeps its
  qualified name but is declared in another module is reported `api-compat:type-module-changed`,
  because consumers of the old artifact lose it. `modules` limits the comparison to the API
  declared in the named module directories (other modules still count as supertypes); a directory
  that is a module neither at the baseline nor in the working tree is an execution error. Not read:
  Gradle `projectDir` remapping, `includeBuild`, and `include` calls built from variables or split
  over several lines; a Gradle project without a build script. Enable the gate only for the modules
  that someone depends on as a library, with `modules`.
- **Java API.** `public` types and members, `protected` members of types that can be extended
  outside their package, interface members, and nested types of API types. Package-private and
  `private` declarations are not API.
- **Kotlin API.** Kotlin visibility applies: a declaration is API when it is `public` (the default)
  or, for a member of an open class, `protected`; `internal` and `private` are not API. A class is
  closed unless it is `open`, `abstract` or `sealed`, and members are closed unless `open`,
  `abstract` or `override`. `object`, `companion object`, `enum class`, `interface`, `data class` and
  nested types are types of their own (`p.Outer.Companion`); an enum's entries are fields. A
  property is its accessors: `val x` is `getX()`, a `var` also has `setX(...)`, and a name such as
  `isReady` keeps `isReady()`, so a `var` that becomes a `val` reports `member-removed`. A `data
  class` also has `componentN()` and `copy(...)`, so adding a constructor property reports the
  removed `copy`. An extension receiver is the first parameter. The top-level functions and
  properties of a package, from every file, are the members of one type, `<package>.<top-level>`,
  because Kotlin callers do not see the file; moving a function between files of a package is not a
  change.
- **Execution errors, never a pass.** Not a Git repository, an unknown `base`, no release tag, a
  baseline that has no sources for the project, a syntax error in a source file at either revision
  (the message names the file and the revision), and an `include` prefix that matches no type at
  the baseline.
- **Findings.** `api-compat:<kind>`, with the qualified type, the member, the signature at the
  baseline and the signature now (or `removed`). Kinds: `type-removed`, `type-less-visible`,
  `type-kind-changed`, `type-now-final`, `type-now-abstract`, `supertype-removed`,
  `type-parameters-changed`, `member-removed`, `member-less-visible`, `static-changed`,
  `return-type-changed`, `field-type-changed`, `signature-changed`, `abstract-method-added`,
  `method-now-abstract`, `method-now-final` and `field-now-final`; for Kotlin also
  `nullability-narrowed` (a parameter that no longer accepts `null`, or a return type that may now
  be `null`) and `default-argument-removed`. A method that moved to an API
  supertype of the project is not reported as removed.
- **Not reported.** Additions, widened visibility, abstract methods that become concrete, added
  `default` methods, annotation, `throws`, parameter-name and constant-value changes, and
  bridge or synthetic members. Narrowing a return type is reported, because callers compiled
  against the old signature break.
- **Limits.** The baseline is the tag's sources, not the published artifact, so a release built
  from other code is not seen. Code generated by annotation processors or Lombok is not read, and a
  type from a library that is not imported by name or on Ward's classpath is left out of both sides.
- **Kotlin limits.** Types are compared as the JVM sees them, so `List` and `MutableList`, or `Int`
  and `Int?` on a parameter, are not told apart by kind: the first pair is the same type, the second
  differs and is reported as a changed or removed member. A return type or property type that is
  inferred from the initializer is unknown: it is never reported as changed, and a `var` whose type
  is inferred has a setter that cannot be matched when the type is written in the other revision.
  A type Ward cannot resolve, including a function type, is compared by its written text. Not read:
  annotations (`@JvmName`, `@JvmStatic`, `@JvmOverloads`, `@file:JvmName`, so the names Java callers
  see are not compared), `typealias`, annotation class elements, `fun interface`, `expect` and
  `actual`, `const` values, `inline` and `suspend`, context receivers, and code generated by KSP or
  kapt.

Init offers `api-compat` to a Java or Kotlin project (Maven or Gradle) when a release tag is
reachable from `HEAD`, and writes `uses = "api-compat"` with no command and no build-file change.
A `[checks.api-compat]` with a `command` runs that command as before; one without a `command` is the
native check.

Applications shipped as binaries, such as CLIs, have no Java API consumers and should not enable
it. In a multi-module build that mixes a library with an application, name the library's modules
with `modules`.

## OpenAPI contract gates

`openapi-lint`, `openapi-diff`, and `openapi-compat` check a committed (contract-first) OpenAPI
spec. Each one needs a `spec` option with the project-relative path of that file.

`openapi-lint` runs Ward's own `ward:openapi/*` rules, which follow the OpenAPI 3.x rules of
Spectral (`spectral:oas` with every rule) and its OWASP ruleset, with the same severities, positions
and messages. It takes no `command`, and a `command` on it is a configuration error (exit `2`). A
warning or an error fails the gate; an `info` finding is a note. OpenAPI 3.0 and 3.1 documents are
supported, and `$ref`s are followed to other files of the project, never fetched over the network. A
Swagger 2.0 document, an OpenAPI 3.2 document, a syntax error or a reference that cannot be read
ends the gate with an execution error that names the file and position. The `ward-rules.toml`
file of the project (or `rules-file`) selects and configures the `openapi.*` rules like any other
rule. `openapi-diff` and `openapi-compat` run inside Ward and take no `command`:

```toml
[checks.openapi-lint]
profiles = ["default", "pre-commit", "pre-push", "ci"]
spec = "src/main/resources/openapi.yml"

[checks.openapi-diff]
uses = "openapi-diff"
profiles = ["default", "pre-commit"]
spec = "src/main/resources/openapi.yml"

[checks.openapi-compat]
uses = "openapi-compat"
profiles = ["pre-push", "ci"]
spec = "src/main/resources/openapi.yml"
base = "origin/main" # the default
```

The gates need no tool. A `command` on `openapi-diff` or `openapi-compat` is a configuration
error (exit `2`).

### Breaking-change rules

The two comparison gates load the spec at the baseline and in the working tree, follow the `$ref`s
of each (the baseline's at its own commit), and run the breaking-change rules
`ward:openapi/<check id>`: one per error-level check of oasdiff 1.37.0, with the same ids. A finding
points at the changed node in the working-tree file. The gate fails on any finding. A spec that
cannot be parsed, a `$ref` that cannot be resolved, a referenced file that is missing at the
baseline, or a Git read failure is an execution error, never a pass. `oasdiff` is not used and
`.oasdiff.*` files or `OASDIFF_CONFIG` change nothing. The rules cover OpenAPI 3.0 and 3.1; the
list is in the OpenAPI rule reference. Sunset dates are judged against today, with no minimum
deprecation period.

### Baselines

| Gate | Compares the spec with |
|---|---|
| `openapi-diff` | The spec at `HEAD`, so it catches a breaking edit before you commit it. In `pre-push` and `ci` everything is committed, so it would compare the file with itself; use `openapi-compat` there. |
| `openapi-compat` | The merge base of `HEAD` and `base`, so only the changes on your branch count. When `HEAD` is that merge base, as on `main` after a merge, it compares with the first parent of `HEAD`. |

A spec that does not exist at the baseline is new: the gate passes and its summary says there was no
baseline.

Ward never fetches:

- Fetch the base branch before pushing.
- Give CI a checkout with the base branch history, for example `actions/checkout` with
  `fetch-depth: 0`. Without a merge base, `openapi-compat` fails and says so.
- A `base` ref that does not exist is a configuration error (exit `2`).

### No exceptions

These gates accept no way to silence a rule, in any profile:

- `openapi-lint` has no inline or tool-level way to silence a rule: `x-lint-ignore` in the spec
  fails the gate, a tool configuration file in the project root has no effect, and a rule is
  switched off only by `exclude` in the committed `ward-rules.toml`.
- `openapi-diff` and `openapi-compat` have no flags and no ignore file: every breaking change the
  rules find fails the gate.

Before running, `openapi-lint` also fails when the spec contains `x-lint-ignore`.

## Structured findings

When `ward`, `secrets`, `compile`, `ward-format`, `tsc`, `mypy`, `swift-build`, or `xcodebuild-test` fails, Ward turns the tool's output
into findings with rule, severity, file, line, column, message, and a rule documentation link when
known. They appear in [JSON](/reference/json-output/) and SARIF output.

| Gate | Source | Maven | Gradle | TypeScript & JavaScript |
|---|---|---|---|---|
| `secrets` | Ward's own findings, with rule, file, line and column | | | |
| `compile` | javac messages in the output | | | |
| `ward-format` | Ward's own findings, one per unformatted file (file only, no line) | | | |
| `tsc` | Compiler diagnostics in the output; the command must pass `--pretty false` | | | |
| `swift-build` / `xcodebuild-test` | Swift compiler errors in the output, with rule `swiftc` | | | |

- Only default report locations are read, and only reports written during the current run. An older
  report is ignored.
- TypeScript, JavaScript, Python and Swift projects keep the reports Ward reads under `.ward/reports/`
  instead of `target/` or `build/`. Stryker's mutation report is the exception: it stays at Stryker's own
  `reports/mutation/mutation.json`, because only Stryker's configuration file can move it.
- A missing or malformed report never changes the gate result; the gate just has no findings.
- `secrets` findings never contain the matched secret or any source text.
- `mypy` reads the JSON lines of `mypy -O json`. Mypy `note` lines are skipped. A missing or unparseable JSON output gives no findings, and the gate result does not
  change. Only the structured formats are read: the command must pass them.
- `tsc`'s pretty output gives no findings. The gate result does not change.
- Swift compiler errors are read without terminal colours, once each even when the compiler
  repeats them in a source excerpt.
- Other gates have no findings yet.

## Partial checks

`ward init` writes a [`[checks.<name>.paths]` table](/configuration/ward-toml/#partial-checks)
for `secrets`, `openapi-lint`, and
`openapi-diff`. After an agent
edit, and for the files a commit stages, a gate:

- is skipped when no edited file is in its `match`;
- runs in full when one of its `full` files was edited;
- is narrowed to the edited files when the tool supports it:

| Gate | Maven | Gradle |
|---|---|---|
| `secrets` | the edited files, scanned in Ward, so uncommitted edits are scanned | same as Maven |
| `openapi-lint`, `openapi-diff` | full, only when the spec is edited | full, only when the spec is edited |

`tsc` and the test runners have no table, so they run in full in `pre-push`
and `ci`.

In a Turborepo workspace, the type-check and test gates have no table and always run in full.


The forms above were verified against the real tools: a path format a tool does not understand
analyzes no files and passes. The full check at the end of an agent turn, Git hooks, and CI always
check the whole project.
