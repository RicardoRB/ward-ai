Configuration uses TOML version 2. Each check is declared as `[checks.<name>]` and must have a
`command`. `<name>` is any non-blank name you choose, and it is what Ward prints and what `--gate`
selects:

```toml
version = 2

[checks.tests]
enabled = true # default: true
command = "./mvnw test"

[checks.integration]
command = ["./mvnw", "verify"]
profiles = ["ci", "strict"]
```

Two checks may run the same tool:

```toml
[checks.coverage]
command = "./mvnw jacoco:check"

[checks.coverage-tests]
command = "./mvnw -pl core jacoco:check"
```

Version 1 files (`[quality-gates.<id>]`, `preset`, top-level `[profiles]`) are rejected. Regenerate
the file with `ward init --overwrite`, or edit it by hand using this page.

## Tool types

Each check has a tool type. The type decides its behavior: how its findings are read, its
prerequisites, its learning keys, and whether `--exclude-spec` selects it. The name does not.

- `uses` sets the type explicitly. It must be a supported type, or the file is rejected.
- Without `uses`, Ward infers the type from `command`. A command that matches no type, or more than
  one, is a plain `command` check: its verdict comes from the exit code, and it has no findings.

```toml
[checks.style]
command = "./mvnw jacoco:check" # inferred: coverage

[checks.architecture]
command = "./mvnw -Dtest=ArchitectureBoundaryTest test" # a filtered test run is not inferred as tests

[checks.lint]
command = "npm run lint" # a plain command check: its verdict comes from the exit code
```

`ward check --format json` reports each result's `name` and `type`.

For Gradle projects, use the Gradle Wrapper when present (or `gradle` when it is not):

```toml
[checks.tests]
enabled = true
command = "./gradlew test"
```

For TypeScript and JavaScript projects, run the locally installed tool through the project's package
manager, such as `pnpm exec`, `npx`, `yarn`, or `bunx`:

```toml
[checks.tsc]
command = ["pnpm", "exec", "tsc", "--noEmit", "--pretty", "false"]
profiles = ["pre-push"]
```

`command` accepts a string or an array of strings. Arrays preserve exact argument boundaries. A
string is parsed into arguments. Neither form is executed through a shell.

## Profiles

- Checks without `profiles` belong to `default`.
- Init-generated configurations assign fast checks to `default`, `pre-commit`, `pre-push`, `ci`, and
  `edit`; slower local checks to `pre-push` and `ci`; and every selected check to `ci`. `pre-push` is
  cumulative.
- `ward check` without flags runs `default`. `ward check --path <file>` without `--profile` runs
  `edit`.
- Select other profiles with `ward check --profile ci,strict`.
- Legacy top-level `[profiles]` tables are unsupported.

The `edit` profile is the set of checks that run after an agent edits a file. See
[Partial checks](#partial-checks).

Unknown check names are errors, and so are checks with no enabled matching check. A selected `edit`
profile with no check belonging to it passes with a warning on stderr, because a hook must not fail
every edit on a configuration without `edit` checks.

## CRAP score limit

A `crap` check needs no `command`. `max` is the largest CRAP score a function may have, an integer
of at least 1 (default 30), and `report` is a project-relative path, or an array of paths, to the
coverage report it reads; without `report` Ward reads the default report of the build tool. See
[CRAP gate](/configuration/gates/#crap-gate).

```toml
[checks.crap]
uses = "crap"
report = ["api/coverage/lcov.info", "web/coverage/lcov.info"]
max = 15
profiles = ["ci"]
```

A `max` that is not an integer of at least 1, or a `report` that is empty or outside the project, is
a configuration error that names the key.

## Mutation score minimum

The `stryker`, PIT `mutation` and `mutmut` checks accept an optional `minimum`, an integer from 0 to
100. When it is set and the tool succeeds, Ward reads the tool's report and fails the check when the
mutation score is below the minimum. See [Stryker mutation score](/configuration/gates/#stryker-mutation-score),
[PIT mutation score](/configuration/gates/#pit-mutation-score) and
[mutmut mutation score](/configuration/gates/#mutmut-mutation-score).

```toml
[checks.stryker]
command = ["npx", "stryker", "run", "--reporters", "clear-text,progress,json"]
minimum = 60
profiles = ["ci"]
```

A `swift-coverage` check requires `minimum`, its lowest line coverage in percent; see
[Swift coverage](/configuration/gates/#swift-coverage).

```toml
[checks.coverage]
uses = "swift-coverage"
command = ["swift", "test", "--show-codecov-path"]
minimum = 80
profiles = ["pre-push"]
```

An `android-coverage` check requires `minimum` the same way; see
[Android coverage](/configuration/gates/#android-coverage).

`minimum` on any other check, a missing `minimum` on `swift-coverage` or `android-coverage`, or a
value that is not an integer from 0 to 100, is a configuration error that names the key.

## Xcode test platform

An `xcodebuild-test` check sets `platform` to `iOS Simulator` or `macOS`, which decides where its
tests run; see [Xcode tests](/configuration/gates/#xcode-tests).

```toml
[checks.xcode-tests]
command = ["xcodebuild", "test", "-scheme", "Shop"]
platform = "iOS Simulator"
```

`platform` can be left out when the command already has `-destination`. Any other value, a missing
`platform` without `-destination`, or `platform` on another check, is a configuration error that
names the key and the allowed values.

## Partial checks

An optional `[checks.<name>.paths]` table controls how a check responds to an edited path passed to
`ward check --path`:

| Key | Meaning |
|---|---|
| `match` | Files the check analyzes, as patterns relative to the project root. If an edited path matches, `args` can narrow the command. |
| `full` | Files that configure the check, as patterns relative to the project root. If an edited path matches, the check runs its normal command. |
| `args` | The narrowed arguments. `{paths}` is replaced with the edited paths as separate process arguments, or as one value joined by `separator`. |
| `item` | How each path is rendered: `{path}` (the root-relative path) by default, or `"**/{name}"` for the file name. `{package}` is the name of the workspace package that holds the path, such as `"--filter=...{package}"` for Turborepo. A path in no package is left out of the items, and a check left with no items runs in full. Identical rendered items are passed once. |
| `command` | Optional. The base command a narrowed check runs, with `args` appended, instead of the check's `command`. Use it when the full command ends with a target that would still be analyzed, such as `mypy .`. |
| `separator` | Optional. Joins the rendered paths into one argument. |

An analysis check (`uses = "ward"`) needs no `args`. When an edited path matches its `match` patterns, the
check runs narrowed to that path: it reports the findings of the edited files and of the files that depend on
them, and keeps its cache for the rest of the project. `full` still runs the whole check.

```toml
[checks.semgrep.paths]
match = ["**"]
full = [".semgrep.yml", ".semgrepignore"]
args = ["{paths}"]

[checks.lint.paths]
match = ["**/*.ts", "**/*.tsx", "**/*.js", "**/*.mjs"]
full = ["lint.config.*", "package.json"]
args = ["{paths}"]
command = ["npx", "lint-tool"]
```

For example, a Semgrep edit receives the root-relative path as its own
argument. A lint edit of `src/app.ts` runs `npx lint-tool src/app.ts` instead of `npx lint-tool .`. Other `args` entries are appended unchanged, and nothing passes through a
shell.

- A `full` match wins over a `match` match, and a check without `args` runs in full when an edited
  path matches its `match`.
- A deleted file counts as an edit of the check, but is not passed in `{paths}`. When every relevant
  edit is a deletion, the check runs in full.
- Paths outside the project root are ignored. A check without `paths` always runs in full.
- `args` requires `match`, `command` requires `args`, every list must contain non-blank strings, and
  `item` must contain `{path}`, `{name}` or `{package}`. The keys `partial`, `inputs` and `config` were renamed to
  `paths`, `match` and `full`; using them is an error that names the replacement. Otherwise
  `ward check` exits with code `2`.

When `edit` runs without edited paths, a check with a `paths` table is skipped and a check without one
runs in full, with a warning on stderr that the `edit` profile expects edited paths.

Verify custom arguments with the real tool: a path format the tool does not understand can analyze
no files and pass.

**Security:** commands are trusted executable code and run with the current user's privileges in
the project root. Review `ward.toml` as carefully as a build script; do not run checks on
untrusted repositories outside a sandbox. See [security](/security/).

OpenSpec checks are optional and independent. Use `uses = "openspec"` for strict active validation
and `uses = "openspec-archived"` for completed-task validation. A configured local executable is
resolved from the target project root and is never silently replaced by a PATH executable. An OpenSpec
check may set `root`, a path relative to the project root such as `"../.."`, to run from the directory
that holds `openspec/`; see [OpenSpec tool validations](/configuration/gates/#openspec-tool-validations).
