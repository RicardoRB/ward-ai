title: Security rules
description: The security rules Ward provides for Java, JavaScript, TypeScript and Python, the weakness each one reports, and what it does not see.
---

Ward reports common security weaknesses in source code with its own rules, so a project needs no
external scanner. Every rule has the id `ward:<language>/<weakness>`, the category
`security`, a CWE id of the weakness, and a catalog row that lists the public documents it was
written from (see the [rule reference](/reference/rules/security/)).

Rules that report injection, broken cryptography, certificate validation bypass, unsafe
deserialization or hard-coded credentials have severity `error` and run in the `standard` and
`strict` presets. Rules that report a hardening gap, such as cookie flags, CORS, CSRF, insecure
random numbers, clear-text transport or dynamic markup, have severity `warning` and run in `strict`
only. Change either with `severity` in `ward-rules.toml`, or skip paths with `exclude-paths`.

## Test files and vendored code

`ward:typescript/hard-coded-secret` and `ward:javascript/hard-coded-secret` skip test sources
(`*.test.*`, `*.spec.*`, and files under `test`, `tests` or `__tests__`), where a literal is a mock
value. Ward reads no minified script (`*.min.js`, `*.min.mjs`, `*.min.cjs`) for any rule. A
vendored library that is not minified is still read: leave it out with `exclude-paths` in
`ward-rules.toml`, for example `exclude-paths = ["frontend/src/assets/private/**"]` under
`[rules.javascript.dom-xss]`. The two rules have no option to read test sources too; the
[`secrets` gate](/configuration/secrets/) reads every text file, tests included, and is the
way to look for real credentials committed in a test.

## How the rules look

**Injection rules** follow untrusted data inside one file. A source, such as a request
parameter, that reaches a sensitive call without passing a sanitizer is reported at the call, and the
JSON and SARIF output list the source, each write that carried the value, and the sink. A value that
is a constant, a number, or the result of a sanitizer of the rule is not reported.

The analysis follows calls between the functions of one file: a function that returns a value from a
source is a source for its callers, and a function whose parameter reaches a sink is a sink for that
argument, to a depth of four calls. A flow that crosses a class in another file, is stored in a field
and read in another function, or goes through an overload of the same argument count is not followed,
so those flows are missed. A finding that crosses a call is reported at the call in the caller. The
sources include the environment, system properties, standard input, sockets, database results and
files, as well as request data. The sources and sinks are written as data in
`taint/java/` and `taint/node/` ([writing taint specs](/reference/taint-specs/) describes the format).

**Configuration rules** report a call, option or setting whose written value is known to be
dangerous, such as `MessageDigest.getInstance("MD5")` or `rejectUnauthorized: false`, and not the
safe form of the same API. They match the code as written: an algorithm name held in a constant, a
renamed import or a value set in another file is not seen, and a setting that is dangerous only by
its absence is reported only where a rule says so, such as a cookie with no `secure` option or an
Express application with no frame protection.

## Kotlin

The Kotlin rules are the injection rules of Java for Kotlin code, and they are taint rules: a value that a
Servlet request getter (`getParameter`, `getHeader`), a Spring handler parameter (`@RequestParam`,
`@PathVariable`, `@RequestBody`), a Ktor call (`call.parameters`, `call.receiveText()`) or console input
(`readLine()`) gives a function, and that reaches the sink of the rule in the same function, directly or
through variables, string templates, safe calls and `?:`, is reported. A value that another function
returns, or that is passed into another function that reaches a sink, is followed, also across Kotlin and
Java files; a call in another file must name the class (`Helper.run(x)`, `Helper().run(x)`) or a `val`
that holds a new object (`val helper = Helper()`, then `helper.run(x)`). A `var`, a declared type and a call
that leaves out a parameter with a default value are not paired.
The rules use the specifications of Java (the types are the same) and `taint/kotlin/sources.toml`.

A lambda has its statements in blocks of its own, so a branch inside it keeps its paths apart. `it`, or the
named parameter, takes the taint of the receiver, and the last expression of the lambda is its value: the
value of the call for `let`, `run`, `with`, `use` and `synchronized`, the receiver for `also`, `apply`,
`takeIf` and `takeUnless`, and both for any other call, so `request.getParameter("x").let { Integer.parseInt(it) }`
is clean. A lambda runs once, where it is written, and may be skipped; a lambda that is stored and called
later is analysed where it is written. An `if`, `when` or `try` that makes a value has its branches in
blocks of their own and gives the value of each branch, and the operands of `&&`, `||` and `?:` follow each
other with a skip edge. A property read such as `request.parameterMap` is also the call of the Java getter
`getParameterMap()`, and the initializer, the delegate, the getter and the setter of a property are analysed
as bodies. A `val` that holds a new object (`val context = InitialContext()`) has that type. A sink whose
argument is a lambda's value is checked where the lambda is written, not inside the lambda. See
[taint specifications](/reference/taint-specs/).
