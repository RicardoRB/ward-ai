---
title: Writing taint specs
description: How a taint rule finds untrusted values that reach sensitive operations, and how to write its specification files.
---

A taint rule reports when a value from an untrusted **source** reaches a **sink** argument inside
one file, following calls between its functions. Sources, sinks and sanitizers are written as data in TOML files, so a rule names the
files it uses and the engine never needs code for each library.

A rule body names its specification files and a message:

```toml
check = "taint"
specs = ["taint/java/sql.toml"]
message = "untrusted data from {source} reaches {sink}"
```

`specs` lists classpath paths. A file that is missing, is not TOML, or has a malformed entry is a
configuration error that names the file and the entry, and the other rules still run. The rule runs
on the data-flow graphs, so it needs the `DATAFLOW` capability.

## The file

A specification file has four tables. Each is an array of tables, and each entry describes one
site:

```toml
[[sources]]
kind = "call"
name = "getParameter"
receiver = "javax.servlet.http.HttpServletRequest"

[[sinks]]
kind = "call"
name = "executeQuery"
receiver = "java.sql.Statement"
arguments = [0]

[[sanitizers]]
kind = "call"
name = "encodeForHTML"

[[propagators]]
kind = "call"
name = "append"
from = ["receiver", 0]
```

- `kind` is `call`, `member` or `parameter`. Sources take all three; sanitizers and propagators
  take `call`. Sinks take `call` and `member-write`.
- `member-write` is an assignment to a property, such as `el.innerHTML = html`. Its `name` is the
  property, its `qualifier` is the object as written, and argument 0 is the assigned value. A
  `member-write` source is a configuration error.
- `name` is the called name, the property name of a member read, or, for a parameter, the
  annotation or decorator name.
- `receiver` is a fully qualified type. It is matched against the receiver type that the file
  resolves for the call.
  In Java, a constructor call such as `new File(name)` is a `call` named `<init>` whose receiver is
  the created type, so `name = "<init>"` with `receiver = "java.io.File"` guards that constructor.
- `qualifier` is the receiver text as written, such as `req`. A text that starts with `*` matches
  any qualifier that ends with the rest, so `*.environment()` matches `builder.environment()`.
- `arguments` is required for a sink and lists the argument positions it guards, counted from 0.
  Other entries cannot name arguments.
- `from` on a propagator lists its inputs, as argument positions or `"receiver"`. The argument
  positions are the arguments that the call stores into its receiver variable, so `list.add(v)`
  with `from = [0]` taints `list` when `v` is tainted. `"receiver"` is checked but does not change
  the analysis yet.

Unknown keys and unknown tables are errors, so a misspelt key cannot silently match nothing.

## Matching

- The `name` must be equal. A parameter entry matches an annotation of the same name.
- When the entry has a `receiver` and the site has a receiver type, the two types must be equal.
- A site with no resolved receiver type matches a `receiver` entry only when the entry also names a
  `qualifier` and the qualifier text is equal. An unresolved receiver never matches by accident.
- An entry with only a `qualifier` matches when the qualifier text is equal. An entry with neither
  matches by name.

Receiver types are resolved from declarations and imports in the file. In Java, a declared variable
resolves through its declared type and the file's imports, and a plain type name such as `Runtime`
resolves the same way. In TypeScript and JavaScript, a name resolves only when it is a named import
(`import { Pool } from 'pg'` gives `pg.Pool`) or is declared with that import as its type or as the
class of its `new` expression. Everything else has no receiver type.

## What counts as a flow

Taint follows the data-flow writes of each function, along normal, branch and exception edges:

- A source call or member read taints the variable it is assigned to in the same statement.
- A write whose statement reads a tainted variable is tainted too, unless the read sits inside the
  argument of a sanitizer call.
- A sanitizer's result is clean.
- A later write that replaces the variable before the sink makes the earlier value unreachable, so
  it does not report.
- A sink argument that reads a tainted variable, or that contains a source call directly, is a
  finding.

Taint does not cross function calls. Each statement is one unit, so a statement that reads a tainted
value and also an unrelated value taints what it writes. This favours reporting over missing a
flow.

## Paths

Each finding carries its path: the source, each write that carried the value on, and the sink, in
that order. The path is deterministic for the same source and specifications. It appears as the
`path` field in [JSON output](/reference/json-output/) and as `codeFlows` in SARIF output.

## Bundled specifications

Ward's own security rules use one specification file per weakness: `taint/java/ward-<weakness>.toml`
`taint/node/ward-<weakness>.toml` and `taint/python/ward-<weakness>.toml`. Each lists the sinks of the platform documentation that the
[security rules](/reference/security-rules/) page names, the argument positions each sink guards,
and the sanitizers of that weakness. The sources are shared: `taint/java/sources.toml` and
`taint/node/sources.toml` and `taint/python/sources.toml`.

In Python a receiver type is the module that an `import` names, so `import subprocess as sp` makes
`sp.run(...)` a call of `run` on `subprocess`, and `from os import system` makes `system(...)` a call
of `system` on `os`. A request object (`request.args`, `request.GET`) is matched by the qualifier
`request`, and a parameter of a function that a route decorator or a FastAPI default such as
`Query()` fills is a source through the annotation `@route`, `@get` or `Query`. A DB-API cursor has
no declared type, so the SQL sinks match the method name on any receiver.

## Limits

- A taint rule follows calls between the functions of one file, and into the files it depends on
  when the rule has the `TAINT` capability (the bundled Java taint rules do), to a depth of four
  calls: a function that returns a source value is a source for its callers, and a function whose
  parameter reaches a sink is a sink for that argument. A call is matched by name and argument
  count. Within a file it has no qualifier, `this` or the owner's name; into another file it names
  the owner, as `Owner.m(x)` and `(new Owner()).m(x)` do. A name that two functions of the file
  share is not followed. In Java the owner carries its package, so two classes with one simple name,
  method name and argument count in different packages are told apart by the import or package that
  the call's type resolves through.
- In Java, a call through a variable, a field or a parameter is followed when the class of the
  receiver is decided: the class the receiver was created as (`Base b = new Impl(); b.run(x)` calls
  `Impl.run`, when every value assigned to `b` in the body is a creation of that class, or a final
  field is initialized so), or else the declared class, when it has a body for the method. A
  receiver declared as an interface or an abstract class and not created in the body is not
  followed, and a method that a subclass overrides is not followed when the receiver is declared as
  the superclass. When several implementations are possible, none is followed, so a flow that only
  one implementation carries is never reported through the others.
- A container that receives a tainted value is tainted: an element or member assignment
  (`a[i] = v`, `box.f = v`, in Java) or a call that a propagator names (`list.add(v)`,
  `map.put(k, v)`, `sb.append(v)`) taints the variable, so a callee that reads it from its
  parameter sees the taint. One tainted element taints the whole container, the order of stores and
  reads is ignored, and a store of a clean value afterwards does not clean it, so this reports more
  than a precise model would. Only a variable named by itself is a container: `this.items`, nested
  members such as `a.b.c`, a static field that another method reads, and a value that is serialized
  and read back are not followed.
- Implicit flows through control conditions are not reported.
- A variable's receiver type comes from the last declaration of its name in the function, which can
  differ from the declaration in scope when block-scoped names are reused.
